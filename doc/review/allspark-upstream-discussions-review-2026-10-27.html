Главный вывод

Allspark уже получил значительную часть полезных upstream-исправлений. Следующий прирост качества даст согласованность жизненного цикла операций: что считается завершённой задачей, кому принадлежит ожидание, какой worker и credential обслуживает запрос, какой контекст действительно получает модель и где фиксируется результат. Для расширенного форка с Factory, RLM, памятью и новыми инструментами эти границы особенно важны.

Приоритет ближайшей итерации: supervisor waits и управление перегрузкой; достоверный terminal result; работа autonomous gate runner; согласованный бюджет контекста; обновление credentials в реальном запросе; единый путь local memory. Затем — диагностика, документация фактических возможностей, lifecycle hooks и восстановление workflow.

3. Приоритет: живучесть долгих RLM-сессий

3.1. Отменённое ожидание продолжает занимать supervisor permit

В связанной с #3783 Issue #3780 описана потеря доступности живого child после длительной непрерывной работы. Код fork.012 подтверждает механизм: caller прекращает wait примерно через 65 секунд, но серверное ожидание может удерживать permit до ответа либо 24 часов. Client commands запускаются detached; disconnect не отменяет эти pure waits. На worker приходится 128 слотов. Затем overload теряет тип и учитывается watcher как unreachable.

Это удержание ресурсов с большой верхней границей, а не бесконечная утечка. Указанные в issue примерно 2,4 часа относятся к сценарию автора; Allspark здесь часами не запускался. Issue закрыта автоматически contributor gate, что не означает исправление. Caller budget, server lifetime, detached dispatch, cleanup, capacity.

Рекомендация: передавать общий deadline/request id; отменять pure wait при уходе клиента; освобождать permit по завершению любой ветки; сохранить typed Busy/Overloaded/Timeout/Unreachable; оставить доступную полосу для status/cancel/shutdown. Отмену при disconnect нельзя автоматически распространить на уже начатые side effects: для них нужен учёт результата с неопределённым исходом, а не слепой повтор.

3.2. Durable identity, live worker и доступность — разные сущности

В #3803 observe видит сохранённую выгруженную root-сессию, а send ищет sibling среди live peers. Отказ происходит раньше существующего wake/resume path. В #3783 ChildRecord сохраняет старый active id; routing уже переписывает payload на новый, поэтому конкретный бесконечный двухсекундный цикл в форке не доказан. Повторное разрешение устаревшего адреса остаётся.

Нужен общий resolver: durable session/child id → текущая binding и worker epoch → разрешённый wake при необходимости. Family authorization и неоднозначность имён должны сохраняться. В UI и ответах инструментов полезно разделять run status, session activity и residency; завершённый run не запрещает новую работу той же сессии. Live-only family, observe catalog, payload rebind.

4. Приоритет: корректный результат автоматизации

4.1. JSON print и Factory

#2975 начиналась как TS report, но получила свежие Rust-свидетельства. В текущем fork terminal classification, влияющая на exit code, остаётся внутри if !json_mode. Нельзя считать код 0 доказательством успеха JSON-задачи. Лучше единый TerminalOutcome для обоих режимов и отдельное представление текста/JSON. Совместимость изменения стоит явно объявить; до него machine consumers должны читать terminal result. Current code.

#3663: первый непустой child answer всё ещё закрепляется; позднейшее обновление в Factory использует в том числе длину текста. Более короткий окончательный ответ не становится старым только из-за длины. При этом отсутствие обязательного output уже корректно проваливает entry: старое утверждение о безусловном done/error:null переносить нельзя. Latch, capture failure, length heuristic.

#3664: foreach объединяет текст результатов, а JSON extractor берёт последний подходящий fenced object. Это подтверждённая потеря структуры many-results, даже если последний объект валиден. Каждый instance должен проходить parse/validation отдельно; aggregate обязан сохранять устойчивый порядок и документированную политику частичных ошибок. Join/capture, reverse candidates.

#3569 дополняет картину: headless idle/quiescence barrier не учитывает уже причитающееся goal continuation за live bash. Не следует ждать любой активный goal бесконечно; нужно ждать конкретные owned continuations и учитывать abort. Вместе эти темы требуют идентичности operation/attempt/terminal message, а не вывода о завершении по текущему idle или первому непустому тексту.

4.2. Autonomous gate runner: новая находка при сопоставлении

#3673 указывает на UTF-8 corruption и panic при обрезке строки внутри многобайтного символа. Оба пути сохранены. Дополнительно выявлен самостоятельный дефект: run_child_process создаёт lazy futures stdout/stderr, но select! ожидает только child exit либо timeout. Reader futures начинают poll только после этого. Команда, заполнившая pipe, может остановиться на записи и получить ложный gate timeout. Последующее чтение до EOF тоже не ограничено исходным timeout, если дескриптор удерживает потомок. Это вывод из порядка polling, без запуска shell. Gate lifecycle, decoder/cap.

Исправление должно одновременно poll process и оба readers, продолжать drain после достижения cap и ограничивать post-exit drain. UTF-8 decoder и ANSI parser нужны с состоянием, отдельно для stdout и stderr. В автономном режиме такой gate служит доказательством успеха или провала; его ошибочный timeout способен направить агента на ненужный ремонт.

5. Приоритет: единый бюджет реального контекста

У #3779 важен комментарий, исправляющий исходную гипотезу автора. Старые Compaction records не добавляются в provider prompt как обычные retained messages. Исправление python-state действительно уменьшает этот источник роста. Остаётся другой разрыв: cut-point walk считает только FileEntry::Message, хотя custom messages и branch summaries присутствуют в model-visible projection. Поэтому trigger и retention используют разную стоимость. Cut-point, projection.

У #3793 две подтверждённые части: exact oMLX overflow с заглавной Prompt не распознаётся текущими regex; explicit maxTokens около contextWindow или больше него может обнулить threshold, который означает disabled. Существующий тест закрепляет это поведение. Недостаточно поправить только арифметику trigger, оставив прежний output budget на wire. Threshold, current test.

Предлагается общий ContextBudget из той же projection, которая отправляется провайдеру: system/tools, история с actual dedup, custom notices, output reserve, headroom. Один расчёт должен определять admission модели, trigger, retained tail и post-compaction accounting. Сохраняются tool-call/result pairing и indivisible groups. Automatic compaction должна проверять продвижение границы и фактический rebuilt prompt; отсутствие прогресса должно давать ограниченный recovery и понятную диагностику. Manual summary update может иметь отдельную политику.

Для Graph/LSP/memory это напрямую связано с agent friendliness: короткие стабильные descriptions, bounded результаты, ссылки на большие artifacts, постепенное раскрытие help. Повторная инъекция большого справочника на каждом раунде ухудшит бюджет и предсказуемость prompt cache.

6. Auth, providers, расписание и platform contracts

Credentials и точная маршрутизация

#3575 и #3669 подтверждают разницу между исправленным ручным /reload и открытым automatic recovery. Свежий preflight проверяет наличие auth, тогда как stream клонирует сохранённый ProviderTarget.api_key. В auth library уже есть refresh и single-flight; нужно довести свежий credential до фактического request boundary. Adapter, manual reload.

Рекомендация: хранить auth reference/generation, разрешать credential на serving path, при 401 сначала перечитать store, затем при необходимости один controlled refresh/retry. Не повторять выполненные tool effects и не заставлять все workers одновременно вращать refresh token. Тест проверяет фактический HTTP bearer после peer rotation, а не только return value auth helper.

#3726: provider resolution сначала выбирает первый case-insensitive match. Для custom Xiaomi и built-in xiaomi это может выбрать чужую route. Exact identity должна иметь приоритет, folding допустим только для однозначного fallback. Проверять provider + API dialect + baseURL + auth source. Resolver.

#3720: fork улучшил payment/rate-limit failover, но итоговая durable ошибка всё ещё может содержать только последний endpoint. Полезен ограниченный структурированный список attempts: выбранная route, исходная причина, backup cause, итог. Это улучшает диагностику без добавления в transcript отдельного шумного сообщения на каждую попытку. Failover, durable outcome.

Mistral Large 4 / GLM 5.3 reasoning (#3584/#3585) — отдельный незакрытый долг от уже починенного chunk parser. Текущие allowlist и None/High mapping ограничивают новые модели. Запросы Kimi/Kilo/Friendli не закрываются добавлением marketing name: нужны проверенные transport и capability metadata, limits и wire fixtures.

Cron и configuration

#3802: time[1..] и negative epoch → u64 сохраняют panic/wrap hazards. Парсер должен возвращать ошибку до записи job на пустом/Unicode/pre-epoch input. Parser.

#3804: matcher явно UTC, schema не хранит timezone. UTC сам по себе допустим; проблема — неявное преобразование пользовательского wall-clock intent и миграция. Добавить явный IANA timezone, versioned semantics и preview следующих запусков. Для legacy rows нельзя автоматически менять смысл. Interval остаётся elapsed duration. Schema, matcher.

#2940: исходный TS crash не переносится на Rust автоматически. Но свежий комментарий указывает на сохраняющиеся Rust-проблемы: периодический scheduler отбрасывает Result через .await.ok(), а mutation захватывает locks всех зарегистрированных partitions. Сначала сделать ошибки видимыми и измерить lock count/contention/p95 в зависимости от числа sessions; затем сужать lock scope с сохранением atomic due-claim. Чужие TS-тайминги не являются оценкой ускорения Allspark. Scheduler, partition locks.

#3735: release check считает любое наличие PI_OFFLINE true, тогда как package/catalog paths парсят значение. Нужен общий parser с false-values и типизированным результатом OfflineSkipped, чтобы offline не выглядел как испорченный manifest. Presence check, boolean parser.

#3473: settings overwrite уже исправлен, но leading BOM по-прежнему не нормализуется в settings/auth/models input. Для malformed JSON нужно сохранить существующую защиту от перезаписи. Settings parse, auth parse, models parse.

#3734: hardcoded NEVER_TOUCH_SOCKET_DIRS исключает product-default директории UID 0/1000. Fork launcher уводит обычный запуск на allspark-daemon.sock, поэтому packaged Allspark не обязан повторять этот симптом; raw binary/dev path сохраняет дефект. Изоляцию тестовой инфраструктуры следует отделить от production discovery, сохранив строгую принадлежность state root. Exclusions, fork socket pin.

Платформы

Windows synchronous Python interrupt (#3775) остаётся разрывом: без pthread_kill cancel ставится в тот же event loop, который блокирует синхронная cell. Нынешний fallback test покрывает await-suspended cell. Windows clipboard (#3702) отправляет UTF-8 в clip; нужен явный Unicode contract. ! streaming (#3613) теряет разрезанные UTF-8/ANSI; состояние decoder должно жить дольше одного read. Details и anchors находятся в platform appendix.

Причина telemetry-dependent Windows exit hang (#3727) пока не установлена. Ветка уже исключает несколько ранних гипотез, включая FileSink и сетевую задержку. Нельзя объявлять исправлением произвольный runtime timeout, позволяющий session writer пережить освобождение lease. Нужны stage traces и bounded optional-exporter teardown с сохранением ownership session writes.

macOS TLS (#3808): первый синхронный native trust-store load может расходовать пятисекундное окно model restore. Кэш сертификатов в процессе уже есть. Полезное изменение — отделить client readiness от catalog network budget и действительно дождаться readiness, а не просто запустить prewarm наперегонки.

7. Дополнительные возможности, которые стоит развивать

7.1. Session diagnostics и объяснение возможностей агенту

Свежие local harness reports #3816/#3719 corroborate прежнюю рекомендацию SessionMemoryContext: worker должен вычислить один session/workspace/artifact/memory context и передать его writer, kernel, refine, digest и recall. Починка helper без production wiring не обеспечивает видимость памяти. Worker composition, local helper.

Полезная новая функция — структурированная диагностика фактической сессии: effective model/route, auth generation без credential, active worker epoch, durable/local memory path, tool availability и причина недоступности, context budget, работающие операции, возраст очереди, последняя compaction и progress state. Человек и агент должны получать одну и ту же проекцию.

Документация каждого Graph/LSP/HybridEdit/JEV workflow должна содержать реальный entrypoint, prerequisites, минимальный пример, bounded result, ошибки и recovery. #3772 показывает bare skill guard в TUI при наличии backend support; #3746 — backend scoped models без редактора. Для Python edit #3572 structured diffs теряются между kernel ExecuteResult и tool result. Native HybridEdit не исправляет другой транспорт автоматически. Diff conversion, tool result shape.

7.2. Наблюдаемость, cache fingerprints и batching

#3731 содержит cache-miss симптом, но не доказанную причину. В fork tools уже сортируются, stable prefix выделяется, prompt строится при создании engine. Вместо предположений добавить fingerprints tools/system-prefix/dynamic-tail на request boundary, route/model/thinking/cache policy и usage. По двум соседним запросам должно быть видно, какой segment изменился, либо что байты стабильны и расследование находится у gateway/provider.

#3359 формулирует полезный запрос: пользовательский OTLP export с отдельной конфигурацией от product analytics. Использовать уже существующие internal events; добавить versioned schema и request/operation correlation. Очереди exporter и ingress должны быть bounded; отключение/сбой exporter не меняет результат задачи. Не обещать, что нынешний telemetry client полностью bounded: per-sink queues ограничены, ingress — unbounded.

#3672: generic batching уже есть, но agent replies оформлены как custom messages и доставляются по одному. Batched-ready replies могут убрать лишние parent turns. Каждый элемент обязан сохранить sender, message id, ordering и receipt; не нужно ждать медленного child, задерживая готовых, или объединять control commands с обычными ответами. Выигрыш измеряется на одинаковой задаче и бюджете, а не числом созданных агентов.

7.3. Lifecycle hooks, external integration и durable workflow

#3200 показывает потребность в Rust-compatible extension contracts: session start, before/after tool, compaction, shutdown, contextual injection, deterministic veto. Внутренний before_tool_call hook уже используется; внешний стабильный adapter отсутствует. Следует развести синхронный pre-effect policy и асинхронных observers. Callback на opaque python_repl не является защитой всех действий Python: file/process/network effects требуют покрытия на соответствующей host boundary или отдельной sandbox policy.

ACP load/resume/fork и несколько сессий на одном соединении (#3624/#3623) — запросы интеграции, не сами по себе ошибки Allspark. Их имеет смысл реализовывать поверх исправленной durable identity и event model, с явным advertised capability, а не объявлять поддержку от наличия session ID в request.

Отдельно подтверждён ACP scope defect: session/set_config_option отправляет SetModel/SetThinkingLevel, а worker сохраняет global defaults. Изменение модели одной IDE-сессии может влиять на последующие сессии. Нужен явный scope=session/default, с session-only поведением ACP, и тест неизменности global settings. ACP wire, worker setters, global save.

#3521 предлагает ранний durable workflow RFC. Полезные паттерны: operation/attempt id, immutable artifact reference, append-only transition evidence, writer fencing и детерминированный recovery. Factory уже имеет FSM/progress, но runtime registry остаётся kernel-local. Сначала ограниченный restartable workflow с двумя-тремя реальными этапами; затем расширение. Это не проверенная многодневная система и не доказательство пригодности всего чужого проекта.

Связь с ранее обсуждавшейся SQLite: использовать её для адресуемых sessions/operations, rebuildable indexes, receipts и outbox там, где чётко определён владелец commit. Не создавать два авторитетных состояния одной сущности одновременно в JSONL и SQL. Для доставки — повторяемая доставка с deduplication/idempotency; универсальное exactly-once выполнение внешних эффектов не обещается.

7.4. Проверяемая память и эффективность RLM

#3711 задаёт правильный вопрос об admission self-refinement: как отличить улучшение от reward hacking и переобучения на собственный judge. Предлагаемый pipeline — candidate → validation → ограниченное применение → promotion/rollback. Память должна хранить scope, происхождение, evidence, version/commit, ограничения и результаты независимой проверки. Сгенерированная рекомендация ещё не доказанная практика.

В форке уже правильно разделены predicted и observed outcome, есть audit, concurrent-update checks и rollback. Следующее ограничение конкретно: evidence заполняется proposal.rationale. Это объяснение модели, а не независимый validation receipt. Обязательный quality admission полезен для автоматического/shared promotion; каждый ручной local note не обязан проходить полный benchmark. Planner.

Для JEV quality gate проверять качество самого judge на заданиях, отличных от тех, которыми он был настроен. #3709 полезна как напоминание: работающая рекурсия не означает превосходство над flat agent. Сравнивать одинаковые задачи, модели и бюджеты; отдельно считать task success, regressions, latency, token cost, environment/harness failures, эффективность cache. Первый обязательный сценарий — задачи без подсказки использовать Graph/LSP/JEV: наблюдать естественное обнаружение и полезность инструмента.

7.5. Контроль содержимого на пути к модели

#3729 спрашивает о секретах из shell config в tool output. Частная очистка MCP diagnostics и content-free product telemetry уже существуют, но ordinary Python stdout/result не проходят общий scrubber. Для задач с credentials полезна единая egress projection перед main model, compaction, refinement, children и JEV; отдельно определяется хранение raw transcript и памяти. Known-secret redaction и opaque references могут уменьшить раскрытие, однако prefix/entropy эвристики не гарантируют обнаружение всех секретов. Проверять synthetic secret fixtures на всех путях, не записывая сами значения в диагностический audit. Python result conversion, MCP redaction.
