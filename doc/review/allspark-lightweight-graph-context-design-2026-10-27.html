Лёгкий графовый слой Allspark: код, архитектура и контекст

Как объединить паттерны GitNexus, codebase-memory-mcp, RuVector и billion-context с существующими Graph, LSP, RLM, JEV, HybridEdit и harness memory.

Рекомендация

Развивать существующий Rust + SQLite graph runtime как общий сервис проверяемых связей и ограниченного отбора контекста. Сначала исправить актуальность и происхождение фактов, ограничить объём реально выполняемой работы, затем связать существующие алгоритмы и ADR с ContextPlan. Следующий новый алгоритм — локальный seeded PPR по необходимости. Leiden и GraphBLAS — факультативные вычислительные пути после измерений.

Усиление графа означает больше полезных типов отношений, лучшее разрешение ссылок и восстановимые основания каждого вывода. Общее число рёбер и modularity сами по себе не показывают, стал ли агент лучше понимать код.

Новые API и численные бюджеты ниже — предложения. Исследование выполнено чтением кода и документов через GitHub, поиском и получением научных карточек через Consensus, проверкой доступных первичных источников. Сборки, индексаторы, модели и бенчмарки не запускались; исходники проектов не изменялись.

3. Что исправить до усложнения графа

3.1. Устаревшие unresolved facts при incremental update

Неразрешённые вызовы записываются как Uses source→source. Incremental reindex удаляет Calls/Imports, но сохраняет Uses; уникальность edge не включает callsite, а INSERT OR IGNORE удерживает прежние свойства. Поэтому замена missing_old() на missing_new() внутри прежнего symbol может оставить старое unresolved-содержимое. Это высокоуверенный вывод по исходникам, без исполненного repro. Запись; cleanup; INSERT OR IGNORE.

Исправление: сохранять callsite facts отдельно от агрегированных graph edges, очищать все прежние факты изменённого файла, иметь отдельный unresolved target/candidate record. Несколько вызовов одной пары могут агрегироваться для алгоритма, но сохраняют occurrences, spans и multiplicity. External endpoint и unresolved marker не должны выглядеть как настоящая рекурсия.

3.2. Единая identity и надёжный dirty set

Manual GraphTool разрешает collision одинаковых basename через canonical-path suffix; auto-index/watch используют basename. Защита register_project_at предотвращает перезапись чужого root, но второй checkout может не обновляться автоматически. При занятой writer lease watcher также может отбросить batch; warm check знает только ранее индексированные files. Новому файлу тогда может не хватить следующего события для обнаружения. Manual identity; auto-index; watch.

Нужны один ProjectIdentity resolver, durable/coalesced dirty paths и retry после lease-busy. Добавление/удаление definitions требует invalidation известных name/unresolved dependencies, а не только уже разрешённых соседей. Branch, worktree path, source hash и index generation — разные координаты.

3.3. Ограничить работу, а не только размер ответа

Trace limit считает выданные steps. Узлы ниже confidence floor всё равно расширяются, поэтому небольшой ответ может стоить большого обхода. Architecture, включая FileTree, сначала загружает все nodes/edges; status также материализует граф ради counts. Обход; architecture materialization; status.

Быстрые исправления: SQL COUNT для counters, files-only путь для FileTree, scoped adjacency, ограничения inspected edges/frontier/bytes, проверка deadline внутри циклов. Shared AST parse cache уже существует; оптимизировать следует reread/DTO/проекции, не обещая устранить несуществующий тройной parse.

5. Лучшие заимствования из codebase-memory-mcp

Компактное представление по умолчанию и дорогая архитектура только по запросу. У донора system_structure запускает отдельный worker; ordinary overview остаётся небольшим. Есть generation checks, deadline, cancellation и bounded cache. Caller; worker/cache.

Typed doc/ADR links и возможность отказаться от уверенного edge. Doc reference недостаточно проверенного tier остаётся unresolved; semantic similarities находятся в candidates, отдельно от Edges. Это особенно подходящий образец для Allspark. family gates; emission/abstention; doc candidates.

ADR как документированное намерение. Status, deciders, supersedes и явные ссылки индексируются; новый ADR сам должен утверждать, что supersedes старый. Принятое решение всё ещё требует проверки реализации. ADR semantics.

Staged repair и previous good generation. Донор ремонтирует dependency closure консервативно, при неопределённости возвращается к full rebuild, публикует staging после успеха. Его clone/copy DB не стоит автоматически переносить в Allspark: нужен контракт атомарной видимости, реализацию выбирать под текущий SQLite writer и размер базы. incremental dispatch; staging.

Наблюдаемые зависимости отдельно от inferred components. CALL_REFERENCE не считается исполнением; связь компонентов раскрывается через indexed-edge witnesses. Контракт projection.

Лёгкость требует своих defaults: у донора initial index использует все cores, RAM budget может составлять заметную долю памяти, architecture projection допускает крупный graph/JSON. Async requests при занятости возвращают retry, а не гарантированно попадают в durable очередь. Переносить следует ownership/admission/status, а не эти ресурсные значения или второй daemon. Workers; memory policy; async admission.

6. Как сделать связи богаче и сохранить компактность

Предлагаю четыре логических слоя внутри существующей системы, с отдельными правилами построения и потребления.

СлойСодержимоеДостоверность и lifecycle
КодDefines/Contains, Imports, Calls, References, Implements, Overrides, Reads/Writes, explicit config/build relationsSource span/hash, extractor/version, resolution basis; обновляется вместе с исходниками
НамерениеADR, constraint, rationale, declared component, supersedes, mentionsДокумент/автор/status/scope/revision; accepted не равно implemented
НаблюденияTestRun, diagnostics, tool artifact, outcome, coverage на конкретном runФакт конкретного исполнения с версией source/config/env
Производные представленияCommunities, flows, SCC DAG, co-change, similarity candidates, ranked packsGeneration/algorithm/options/coverage; перестраиваются, не заменяют исходные факты

Самые выгодные новые связи: trait/interface→implementation; callback/reference отдельно от вызова; ADR section→конкретный symbol/module; правило→наблюдаемая dependency; test run→проверенные версии; ошибка/решение→source evidence. Исторический co-change полезен как слабый навигационный сигнал: учитывать ограниченное окно commits, размер commit и исключать массовые formatting/vendor изменения.

Для общей связи нескольких объектов использовать hub node. Если ADR относится к 200 symbols, достаточно 200 MENTIONS к одному ADR; попарная clique дала бы 19 900 отношений без новых исходных оснований. То же относится к Module, Community, Flow, TestRun. Hypergraph-представление здесь можно получить обычными incidence links в текущем property graph.

Предлагаемый edge/fact contract: scope; source/target IDs; relation; occurrence/span; source digest; extractor/resolver version; resolution status/reason; applicability/config; generation; refs на наблюдения. Хранить shared provenance и source text отдельно от каждого edge. Aggregated edge хранит multiplicity и ссылки на occurrences.

Численная confidence эвристики не является калиброванной вероятностью. Компонент, найденный clustering, не становится официальной архитектурной границей. Транзитивно найденный путь — статическая возможность в заявленном scope, а не доказательство реально исполненного workflow.

Не включать по умолчанию all-pairs distances/betweenness, перечисление всех простых путей, глобальный min-cut, GNN и dense similarity matrix. Материализация A² может породить множество новых ненулевых элементов; явные пути могут расти комбинаторно. Для ответа агенту достаточно нескольких ограниченных и объяснимых путей.

Consensus даёт основания для выбора направления, но не измерение Allspark: Leiden исправляет проблему плохо связных сообществ Louvain [1]; EdgePush показывает преимущества более мелкой обработки weighted edges для локального PPR [2]; LabelRankT исследует инкрементальную label propagation [3]. Эти результаты не позволяют обещать тот же выигрыш на графе конкретного Rust workspace.

GraphBLAS: сначала модель вычислений

Полезны masked sparse matrix-vector operations: Boolean semiring для достижимости, plus-times для распространения веса, mask для ограничения frontier. Можно сначала выразить эти операции над компактной Rust adjacency и сохранить интерфейс для будущего backend. SuiteSparse:GraphBLAS — отдельная C-библиотека с OpenMP и вариантами JIT/build, а не бесплатное ускорение любого обхода. Его подключение оправдано повторными крупными вычислениями; в оценку включать экспорт графа, копии памяти, первый запуск и oversubscription. [4], официальный проект.

Что взять из RuVector

Самая подходящая идея — coarsening с явной картой принадлежности и агрегированием связей между группами. Агент начинает с компактного обзора, затем раскрывает cluster → file → symbol → исходный fragment. Condensation implementation сохраняет membership и агрегирует boundary edges; это полезный образец структуры данных.

В Allspark агрегация должна сохранять направление и тип: ключ (source cluster, target cluster, relation, resolution class), число исходных occurrences и ограниченный набор witness refs. У донора boundary aggregation нормализует пару регионов как undirected; буквальный перенос потеряет направление зависимостей. Укрупнённый граф служит навигации, полный граф остаётся источником точных проверок.

Default WeakBoundary удаляет достаточно слабые связи и находит компоненты; это не универсальный архитектурный детектор. Собственный README отмечает дорогую деградацию рекурсивного global min-cut. Compact representation с малыми IDs и bitsets относится к ограниченному локальному графу, а не к обещанию уместить любой репозиторий в 8 KB.

Переносить целиком ruVector-graph ради нескольких алгоритмов не требуется: его default full features включают дополнительные подсистемы. Копировать стоит проверенный принцип, а минимальную реализацию и её стоимость выбирать под Allspark. Sparsification допускается в derived navigation projection; удаление исходных связей из canonical graph ухудшит impact analysis и объяснимость.

8. Архитектура лёгкого runtime

Один Rust graph service, один владелец индекса на canonical worktree, существующая SQLite как хранилище фактов и метаданных. Python RLM, native GraphTool, LSP integration, JEV и UI обращаются к одному сервису. Не нужны отдельные владельцы графа, дополнительный daemon или ещё одна СУБД ради этих паттернов.

КомпонентОтветственностьКогда выполняется
Fact writerSource hashes, occurrences, resolution provenance, atomic publication; сохраняет dirty paths при занятом leaseИзменённые файлы, bounded batches
Shared job schedulerSingleflight по scope/generation/options, bounded CPU executor, priorities, cancellation, statusПо запросу / idle; не при каждом старте session
Derived view builderSCC, clusters, flow views, compact adjacencyЛениво, с byte admission до allocation
GraphEvidenceResolverSeeds → typed expansion → ADR/observations → evidence refs + coverageВ рамках бюджета конкретной задачи
ContextPlanОбщий token budget, selection, materialization, diagnostics и фиксированный итоговый payloadПеред принятиями решений о compaction и отправкой модели

Async и lazy решают разные задачи. Async освобождает ожидание I/O; CPU-графовый алгоритм всё равно выполняет ту же работу. Его следует запускать на небольшом ограниченном executor. Lazy откладывает необязательную работу: LSP только для выбранных неоднозначностей, clustering только при запросе/idle, JEV только для небольшого подготовленного пакета, embeddings только по явной необходимости.

Singleflight в памяти процесса не заменяет существующий cross-process writer lease. Job key должен включать canonical project/worktree identity и ожидаемую generation; более новая желаемая generation вытесняет устаревшую. Отмена одного subscriber не отменяет общий job для остальных. При отказе lease dirty set остаётся и перепланируется; generation, подготовленная по устаревшему snapshot, не публикуется как новая.

Согласованность должна охватывать исходники. SQLite snapshot или index epoch сами по себе не фиксируют рабочее дерево и LSP buffers. Для evidence pack нужны source hash manifest и использованные LSP document versions. Если выбранный файл изменился при materialization, пакет следует пересобрать или пометить partial; apply использует повторные precondition checks. Установка epoch только в конце не делает видимость предшествующих autocommit-изменений атомарной.

Стартовые бюджеты — проектные параметры, не результаты измерений

Эти числа относятся к предлагаемому дополнительному графовому бюджету. Они не являются ограничением суммарного RSS Allspark, SQLite, LSP и моделей; реальную настройку выбирать после измерений на целевом железе.

Оценка компактного adjacency: для N=100 000 и E=1 000 000 directed edges массивы u64 offsets + u32 targets + f32 weights требуют примерно 8,8 MB в одном направлении, 17,6 MB для forward + reverse. Это арифметика массивов, без ID maps, строк, provenance, allocator, SQLite и временных копий. Для сравнения, только 100 000 × 384 float32 embeddings — 153,6 MB. Поэтому adjacency можно строить для hot projection; обязательный embedding каждого symbol не подходит исходной цели.

При rebuild одновременно могут жить SQL rows, старый и новый CSR, frontier и ContextPack. Нужен общий admission перед allocation, а не отдельный «64 MiB cache» для каждого компонента. SQLite остаётся хранилищем, но не следует дублировать весь граф в RAM каждой agent session.

Scope проверяется при search, resolve, expand и direct ref read, а не только на первом FTS запросе. Это относится и к ADR lookup по ID, и к shared caches. Если FTS BM25 использует общие corpus statistics, project-filtered result всё ещё зависит от global FTS epoch; кэш должен учитывать это либо использовать явно project-local ranking. В существующем поиске степень уже считается с project filter; улучшение здесь — bulk aggregation до trim, а не исправление якобы отсутствующей изоляции. FTS и degree.

9. Связка с billion-context, JEV, RLM, LSP и HybridEdit

Практический смысл billion-context в этой архитектуре — долговечный адресуемый корпус исходных данных и маленькая рабочая проекция. Граф ускоряет навигацию и объясняет выбор; ContextPlan решает, какие материалы попадут в конкретный model request. Масштаб хранилища сам по себе не увеличивает внимание модели и не гарантирует recall.

  1. Task/diff seeds. Точные symbol/path refs, текущая ошибка, FTS по вопросу и затронутые файлы. Не запускать глобальное семантическое расширение на каждый turn.
  2. Typed expansion. Выбрать связи по задаче: impact — входящие зависимости; implementation — trait/override/call; architecture — imports/SCC/ADR; debugging — diagnostics/observed tests. Сохранить witness paths и unresolved coverage.
  3. Evidence attachment. Добавить подходящие ADR sections, constraints, проверенные observations и кандидаты harness memory с их собственными validity conditions.
  4. Materialization. Загрузить выбранный текущий source, проверить hashes/LSP versions, построить bounded package. Долговечный исторический ref раскрывает прежний snapshot, но перед редактированием нужен текущий файл.
  5. Optional JEV. Оценить полезность пакета / ответ на конкретный criterion, сохранить advisory результат. Timeout и cache miss не превращаются в запрет простой навигации.
  6. Frozen ContextPlan. Учесть все source fragments, summaries, tool descriptions, TaskState и output reserve одним token budget. По этому же плану принимать решение о compaction и строить диагностический snapshot.
  7. LLM / RLM. Получить компактный pack и ограниченный host API для раскрытия refs. Python не становится вторым владельцем SQLite, graph или LSP.
  8. HybridEdit / LSP. Использовать существующий edit planner с исходными spans/hashes/config. Preview и apply связаны одним plan ID/digest; stale preconditions вызывают replan.
  9. Outcome. Update dirty facts и targeted validation. Только проверяемый результат создаёт observation; memory lesson хранит источники и validity conditions, а не только уверенное объяснение модели.

JEV: полезный второй фильтр, ограниченная роль

Сегодня graph rerank получает query, qualified name, kind и file; исходного тела и content revision в этом state нет. Это оценка релевантности metadata, не подтверждение семантики кода. Текущее состояние. Следующее развитие — дать JEV небольшой выбранный source/evidence pack, а не весь граф. Проверку edit preconditions и фактический исход теста оставлять детерминированному runtime.

Перед увеличением JEV state нужно исправить память кэша: текущий cache хранит canonical state в key для разных questions, ограничивается количеством записей и очищает всю карту у soft cap. Большие пакеты будут многократно дублироваться. Предпочтительны state digest, interned immutable state, byte budget и LRU/segmented eviction.

RLM и PyO3

Для этой задачи не требуется прямая связка Python ↔ Rust graph objects через PyO3. Уже существующий host_request позволяет выдать bounded операции: context, explain, resolve, expand, source read. Один Rust service сохраняет leases, cache, budgets и identity. PyO3 можно оценить позже для измеренного горячего потока численных массивов; для небольших evidence packets стоимость дублирования lifecycle и объектов важнее неподтверждённой экономии вызова.

Дружелюбность к агентам

Развивать существующий graph tool через несколько task-oriented actions, а не добавлять десятки слабо документированных tools. Названия ниже предлагаемые:

  • graph.context — собрать explainable pack под вопрос и бюджет;
  • graph.explain_change — затронутые symbols, witness paths, relevant ADR/tests, unresolved areas;
  • graph.architecture — declared/observed overview, cycles/layers и раскрытие cluster;
  • graph.expand — раскрыть конкретный ref с теми же scope и budget controls.

Capability manifest следует строить из фактически включённых tools/actions и profile exclusions. В начале session достаточно короткой карты «когда использовать Graph, LSP, HybridEdit, JEV и RLM»; подробные schemas/examples раскрываются по запросу. ContextPack возвращает next actions вместе со стоимостью/ограничениями и coverage. Это делает новые функции обнаружимыми, сохраняя небольшой prompt.

10. Понимание архитектуры и ADR

Поддерживать две независимые перспективы. Declared: accepted ADR, explicit constraints, правила зависимостей и объявленные component boundaries. Observed: текущие imports/calls/references, SCC, tests и clusters. Несовпадение перспектив — повод для объяснения и проверки.

Пример: ADR запрещает прямую зависимость UI → persistence. Если правило формализовано, действует в этом scope и текущая witnessed edge показывает запрещённый import, можно показать архитектурное нарушение. Если LLM лишь интерпретировал расплывчатую фразу или clustering отнёс файлы к разным группам, вывод остаётся candidate. Отсутствие найденной связи при неполном индексе не доказывает соблюдение правила.

Структурные зависимости полезно сочетать с folders, build manifests, документацией и code text — такой подход поддерживает исследование architecture recovery через information fusion [5]. История commits/issues помогает восстанавливать часть решений [6], но восстановленное объяснение нельзя автоматически объявлять авторитетным ADR.

Наиболее ценные новые функции: «почему этот модуль затронут», «какое принятое решение применимо к правке», «какие проверки покрывают изменённую область», «какие ссылки устарели», «какую часть прежнего контекста восстановить после compaction». Они используют общие факты и разные bounded projections, вместо отдельной системы памяти для каждой функции.

Если выделять один первый функциональный срез, это «объяснение изменения»: выбранный diff → несколько exact symbols → ограниченный reverse impact → применимые ADR → релевантные проверки → текущие fragments → ContextPlan. Он проверяет почти все нужные seams и даёт понятную пользу без ожидания полного «семантического графа всего».

Не начинать с полного interprocedural points-to, универсального runtime call graph или извлечения всех Reads/Writes для всех языков. Нужны language-specific quality gates: точные supported случаи сначала, неоднозначности как unresolved/candidate, LSP refinement для выбранных узлов. Graph coverage должен сообщать, какие языки/отношения/config поддержаны и где анализ неполон.

Проверки, которые действительно снимают риски

  • Canonical parity full vs incremental: add/delete/rename/alias/body-only edit; исчезнувший unresolved call; новая definition, разрешающая прежний unresolved; occurrence multiplicity. Сравнивать normalized facts, не только counts.
  • Два worktree с одинаковым basename: manual indexing, auto-index и watcher должны использовать один identity contract для каждого worktree.
  • Новый файл появляется во время занятого writer; после этого нет событий. Он всё равно должен попасть в индекс.
  • High-fanout/low-confidence graph, ограниченные bytes/edge scans, cancel в середине обхода. Ограничение output не считается ограничением работы.
  • Concurrent source change, stale LSP version, stale graph generation: pack/apply отклоняет или явно пересобирает выбранные данные.
  • Саморекурсия и external-call marker не должны давать одинаковый архитектурный вывод.
  • Superseded ADR, ambiguous doc mention, co-change и similarity candidate не становятся подтверждёнными dependency facts.
  • Неполный индекс не должен выдавать «безопасно удалить» на основании пустого списка callers.
  • После двух compactions и restart сохраняются TaskState, durable refs и constraints; текущий source не подменяется историческим snapshot.
  • Изменившийся source/config/env инвалидирует применимость тестового observation и memory lesson, даже если текст задачи похож.

Как измерять результат

Сравнивать один и тот же набор задач: baseline → P0/P1 → typed evidence packs → LPA/PPR → optional Leiden/backend. Измерять cold/warm latency, p95, peak/idle RSS, examined edges, invalidation/rebuild cost, source recall, долю корректно объяснённых зависимостей, пропущенные затронутые tests, успех правок и восстановление после compaction. Контролировать случайные seeds и corpus revisions. Рост числа рёбер, cache hit rate и красивые clusters сами по себе недостаточны.

Препринт 2026 года о dynamic Leiden показывает, что «инкрементальный» алгоритм тоже может приблизиться по цене к полному пересчёту; новые сложные схемы affected-set maintenance имеет смысл оценивать лишь после простого bounded baseline. [7] Он включён как исследовательский ориентир, не как требование к ближайшей версии.

13. Границы оценки и решение

Это source-level архитектурная оценка зафиксированных commits, выполненная 27 октября 2026. Найденные ветви и нарушения контрактов подтверждены чтением соответствующего кода; runtime воспроизведение, сборка и нагрузочные тесты не проводились. Предлагаемое развитие сохраняет текущий стек: Rust graph runtime + SQLite + bounded shared jobs + typed provenance + lazy views + единый ContextPlan. GitNexus даёт полезные механизмы разрешения и объяснения связей, codebase-memory — lazy lifecycle и связь документации с кодом, RuVector — компактный многоуровневый обзор, исследования — основания выбора алгоритмов. Максимальный ближайший эффект ожидается от актуальных фактов и их доставки агенту в нужный момент; усложнение математического backend идёт после этого.
