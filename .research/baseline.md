# Лучшие практики 2025–2026: меньше ошибок tool calling и меньше токенов для coding agents

Дата: 2026-10-12. Scope: research-only для Prime Agent; репозиторий не менялся. Файл сравнивает внешние claim-и и текущую кодовую поверхность Prime. Числа от вендоров помечены как vendor/internal, не как независимый эффект Prime.

## Как читать источники

- **Claim** — внешняя рекомендация или benchmark. Для web-фактов указан URL. Для уже существующих локальных заметок и Prime-кода указан `file:line`.
- **Code-evidence** — что уже есть или чего не видно в Prime по исходникам. Это не runtime-бенчмарк.
- Источники сверялись несколькими каналами: Exa full fetch, Keenable/Tavily snippets/extract, websearch для точных URL/arXiv. В спорных местах ниже предпочитаются официальные URL.

## Короткий вывод

1. **Самый большой token-win для Prime уже почти доступен через Python PTC:** держать MCP/tool orchestration в `ipython`, делать `mcp.search_tools/describe_tool/call_tool`, `asyncio.gather`, фильтрацию и агрегацию в Python, а в контекст возвращать только короткий результат. Это ровно класс проблем Anthropic описывает для MCP: tool definitions/results могут занимать 50k+ токенов, а code execution снижает контекстную цену за счёт on-demand loading и промежуточной обработки вне модели (https://www.anthropic.com/engineering/code-execution-with-mcp; https://www.anthropic.com/engineering/advanced-tool-use).
2. **Для edit-вызовов не надо слепо переходить на unified diff.** Aider показывает, что whole-file проще, но дороже; Diff-XYZ показывает, что search-replace сильнее для крупных моделей во многих diff-задачах; EDIT-Bench показывает, что реалистичный контекст важнее искусственного edit-format микробенча (https://aider.chat/docs/benchmarks.html; https://arxiv.org/abs/2510.12487; https://arxiv.org/abs/2511.04486). Prime уже использует exact replacement, unique-match, serial same-file queue и подробные edit errors (`crates/pa-core/src/tools/edit.rs:15-50`, `crates/pa-core/src/tools/edit_diff.rs:196-242`, `crates/pa-core/src/tools/file_mutation_queue.rs:1-54`).
3. **Schema/strict decoding лечит interface misuse, но не semantic misuse.** OpenAI Structured Outputs говорит о 100% schema-eval для `gpt-4o-2024-08-06` против <40% у `gpt-4-0613`, но также говорит, что schema не предотвращает ошибочные значения и несовместима с parallel function calls в этом режиме (https://openai.com/index/introducing-structured-outputs-in-the-api/). Schema First pilot 2603.13404: schema+diagnostics снижали interface misuse, но success остался zero и semantic misuse не ушёл (https://arxiv.org/abs/2603.13404).
4. **Ошибка tool call должна быть подсказкой для саморемонта.** Prime уже возвращает tool errors как model-facing text (`crates/pa-core/src/tools/tool_definition.rs:54-63`, `crates/pa-core/src/tools/tool_definition.rs:87-103`) и edit errors уже формулируются как “exact text”, “unique”, “provide more context” (`crates/pa-core/src/tools/edit_diff.rs:196-236`). Это надо распространить на skills/PTC/MCP wrappers: field path, expected/allowed, found, valid candidates, retryability, cap identical retries.
5. **Малый активный tool set важнее большого каталога в контексте.** Anthropic Tool Search Tool claim: `defer_loading` дал 85% token reduction и Opus 4 49%→74% на internal MCP evals; OpenAI рекомендует держать <20 functions initially and use tool search; Gemini Cloud рекомендует 10–20 active tools and dynamic tool selection (https://www.anthropic.com/engineering/advanced-tool-use; https://platform.openai.com/docs/guides/function-calling; https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/tools/function-calling). Prime MCP уже работает как on-demand Python surface, а не как top-level provider tools (`prime-agent-runtime/src/rlm/mcp.py:1-15`, `crates/pa-core/src/prompts/system_prompt.rs:379-395`).

## Claim notes by topic

### Anthropic advanced tool use

- Tool Search Tool is a high-effect pattern only when the tool catalog is large: Anthropic says use it for >10k tool-definition tokens, tool-selection accuracy issues, MCP multi-server systems, or 10+ tools; less useful for small fixed toolsets (https://www.anthropic.com/engineering/advanced-tool-use). In current Prime, the provider-visible built-ins are small (`bash`, `edit`, `ipython`), so the direct target is skills/MCP discovery, not core built-ins (`crates/pa-core/src/tools/tool_definition.rs:107-122`).
- Programmatic Tool Calling maps almost directly to Prime’s Python REPL: Anthropic’s PTC claim is “code orchestrates tools and only final output enters context” (https://www.anthropic.com/engineering/advanced-tool-use). Prime’s `ipython` is persistent, supports top-level `await`, and tells agents to run shell via `bash()`/project native environment (`crates/pa-core/src/tools/ipython.rs:339-354`).
- Tool Use Examples are useful for complex optional/nested conventions, but they are token-bearing examples; Anthropic recommends 1–5 concise examples and only where schema is insufficient (https://www.anthropic.com/engineering/advanced-tool-use). Prime should not add examples to every tool by default.

### Edit-format evidence

- Aider’s old benchmark is useful as a warning, not a Prime law: function-call edit formats performed worse in that GPT-3.5/GPT-4 experiment, while whole-file was reliable but token-heavy (https://aider.chat/docs/benchmarks.html). Prime should not infer “function calling is bad”; newer strict decoding and model training changed the interface layer, and Prime’s edit function is not the same as Aider’s old function format.
- Cursor’s Fast Apply separates planning from application and uses a specialized 70B model/speculative edits around full-file rewrite, claiming ~1000 tokens/s, ~13x over vanilla Llama-3-70B and ~9x over previous GPT-4 speculative-edit deployment (https://cursor.com/blog/instant-apply). This is a specialized apply-model architecture, not a reason to make the main reasoning model emit whole files in Prime.
- EDIT-Bench adds realistic context: 540 problems, 40 models, only one model over 60%, performance varies up to 11% with context information, and highlighted code helps more than cursor in their ablation (https://arxiv.org/abs/2511.04486). Prime edit evaluation should include observed file context/highlights, not only patch parser success.
- Diff-XYZ isolates diff understanding and finds search-replace best for larger models across most tasks, udiff variants competitive, and small open models benefit little from format choice (https://arxiv.org/abs/2510.12487). This supports per-model/per-task edit policy, not one universal edit format.

### Structured outputs and diagnostics

- OpenAI strict/Structured Outputs is strongest for syntactic contract adherence; OpenAI itself lists limitations: unsupported JSON Schema subset, first-schema latency, refusal/max-token breaks, no guarantee of value correctness, and incompatibility with parallel function calls in Structured Outputs (https://openai.com/index/introducing-structured-outputs-in-the-api/).
- Schema First 2603.13404 is the right caution for Prime: schema and diagnostics reduce interface misuse but semantic action quality remains the dominant bottleneck (https://arxiv.org/abs/2603.13404). Therefore Prime should log separate counters: interface misuse, execution failure, semantic misuse, retry recovery, token overhead.

## Prime code-evidence: current affordances and gaps

- Model-facing tools have name/description/parameters and optional argument normalization/execution mode (`crates/pa-core/src/tools/tool_definition.rs:87-103`). This is the right place for schema tightening and model-facing error text.
- Tool errors surface as `Err` model-facing text, not hidden variants (`crates/pa-core/src/tools/tool_definition.rs:54-63`). This makes retry-with-error-message feasible without new protocol.
- `edit` schema already rejects ambiguous/large connected edits at the prompt/schema level: exact unique `oldText`, non-overlap, same-original matching, no large unchanged regions (`crates/pa-core/src/tools/edit.rs:15-50`).
- `prepare_edit_arguments` supports legacy top-level `oldText/newText` and JSON-string `edits` normalization (`crates/pa-core/src/tools/edit.rs:107-150`). This is helpful backward compatibility, but strict-mode pilots must decide whether to keep or remove such repair before provider strict validation.
- Exact edit application produces actionable not-found/duplicate/no-change errors (`crates/pa-core/src/tools/edit_diff.rs:196-242`). This is a model-friendly diagnostic pattern to copy into skills.
- Same-file mutations serialize; different files can proceed (`crates/pa-core/src/tools/file_mutation_queue.rs:1-54`). This supports safe parallel tool calls.
- Agent loop already supports parallel tool execution and falls back to sequential if any call is sequential (`crates/pa-agent/src/agent_loop/tools.rs:31-72`). `ipython` opts into sequential because the kernel is single-threaded (`crates/pa-core/src/tools/ipython.rs:520-528`).
- MCP is already a Python on-demand surface: list/call/discover/search/describe (`prime-agent-runtime/src/rlm/mcp.py:1-15`, `prime-agent-runtime/src/rlm/mcp.py:700-756`). This is Prime’s closest existing analogue to Tool Search Tool.
- Skills are currently advertised in the prompt inventory when file access exists (`crates/pa-core/src/prompts/system_prompt.rs:172-194`, `crates/pa-core/src/skills/mod.rs:215-235`). If skill count grows, skill search/defer-loading is likely a better ROI target than MCP, because MCP schemas are not injected as top-level tools.
- OpenAI strict mode is not currently on by default in observed converters (`crates/pa-ai/src/providers/openai_responses_shared.rs:357-379`, `crates/pa-ai/src/providers/openai_completions/convert.rs:400-411`). This is an explicit experiment candidate.
- Bash output already uses bounded memory and spill/full-output path (`crates/pa-core/src/tools/bash.rs:173-190`, `crates/pa-core/src/tools/output_accumulator.rs:1-2`, `crates/pa-core/src/tools/output_accumulator.rs:150-152`, `crates/pa-core/src/tools/output_accumulator.rs:244-247`). Do not add another full-output store; improve recall/pointers if needed.

## Recommended Prime experiments, ordered by effect/price

1. **PTC-by-default playbook for MCP/skills.** For tasks with 3+ tool calls or large raw results, prompt/skill docs should say: discover with `mcp.search_tools/describe_tool`, run calls in Python, aggregate/filter locally, return concise final evidence. Measure input tokens, output tokens, retry count, wall time, verified success. External basis: Anthropic PTC/token claims (https://www.anthropic.com/engineering/advanced-tool-use; https://www.anthropic.com/engineering/code-execution-with-mcp). Prime basis: `ipython` and `mcp.call` surfaces (`crates/pa-core/src/tools/ipython.rs:339-354`, `prime-agent-runtime/src/rlm/mcp.py:507-516`).
2. **Structured diagnostics standard for every tool/skill error.** Define a small text/JSON pattern: `error_type`, `field/path`, `expected`, `found`, `valid_values/candidates`, `retryable`, `next_action`. Keep raw traceback hidden unless asked. External basis: Anthropic helpful errors and Schema First diagnostics (https://www.anthropic.com/engineering/writing-tools-for-agents; https://arxiv.org/abs/2603.13404). Prime basis: model-facing error path and edit errors (`crates/pa-core/src/tools/tool_definition.rs:54-63`, `crates/pa-core/src/tools/edit_diff.rs:196-236`).
3. **Strict schema pilot for OpenAI Responses on one or two tools.** Start with `edit` after schema audit; do not enable globally until `additionalProperties:false`, all-required/nullable fields, and provider compatibility are checked. External basis: OpenAI strict requirements/limitations (https://platform.openai.com/docs/guides/function-calling; https://openai.com/index/introducing-structured-outputs-in-the-api/). Prime basis: strict currently false (`crates/pa-ai/src/providers/openai_responses_shared.rs:357-379`).
4. **Skill search / deferred skill inventory.** Keep a tiny “skill search/list relevant skills” tail instead of full inventory when many skills are installed. External basis: Tool Search Tool and OpenAI/Gemini small active set guidance (https://www.anthropic.com/engineering/advanced-tool-use; https://platform.openai.com/docs/guides/function-calling; https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/tools/function-calling). Prime basis: current skill inventory injection (`crates/pa-core/src/skills/mod.rs:215-235`).
5. **Evidence-bound edit handles.** Keep exact replacement, but add optional observed range/hash guard to reduce stale/ambiguous edits. External basis: Diff-XYZ search-replace and EDIT-Bench context sensitivity (https://arxiv.org/abs/2510.12487; https://arxiv.org/abs/2511.04486). Existing local synthesis already flags this as the useful delta over “rewrite tools” (`/tmp/prime-architecture-research/PATTERNS.md:49-55`).
6. **Separate interface vs semantic telemetry.** Track malformed/missing/type/enum vs runtime precondition vs schema-valid semantic misuse. External basis: Schema First taxonomy (https://arxiv.org/abs/2603.13404). Prime basis: baseline says evaluation should include retry amplification and verified completion, not only self-assessment (`/tmp/prime-architecture-research/baseline.md:16`).

## Minimal policy for agents using Prime today

- Use `ipython` as orchestration memory and code executor when a task needs loops, conditionals, many MCP calls, or large result filtering; do not stream every raw result back through assistant text (`crates/pa-core/src/tools/ipython.rs:339-354`; https://www.anthropic.com/engineering/code-execution-with-mcp).
- Before calling a generic MCP server with many tools, use `mcp.search_tools` or `mcp.describe_tool`, not `mcp.list_tools` dumps, unless the server is tiny (`prime-agent-runtime/src/rlm/mcp.py:700-756`; https://www.anthropic.com/engineering/advanced-tool-use).
- For edits, prefer exact small replacements grounded in a recent read/search result; if replacement fails, read the exact failing region and retry once with more context, not a broad whole-file rewrite (`crates/pa-core/src/tools/edit.rs:15-50`; `crates/pa-core/src/tools/edit_diff.rs:196-236`).
