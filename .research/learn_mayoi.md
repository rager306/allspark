## Часть 1. Как реализовано у них

### П1. Инкрементальная переподсветка — `internal/highlight/highlight.go`

Суть: Chroma-лексер гоняется в фоновой горутине; после правки переразбирается
только окрестность изменения, и результат принимается только если доказано,
что он совпадает с прежним выше по файлу.

Механика по строкам файла `internal/highlight/highlight.go`:

- `lex()` (стр. 144) — потоковый разбор с callback'ом `done(row, lines) bool`:
  Chroma отдаёт токены лениво, поэтому лексинг можно оборвать на середине
  файла, и строки до места обрыва корректны.
- Константы `WholeFile=6000, Context=400, Below=200` (стр. 268–270): файлы до
  6000 строк лексируются целиком, длиннее — окно вокруг видимой области.
- `Quiet = 300ms` (стр. 276): когда правки стихли, полный перелексинг всего
  диапазона «дочищает» строки, чьё состояние нельзя вывести из окрестности
  (мультистрочные строки/комментарии с редкими лексерами).
- `Highlighter` (стр. 280): хранит `version`, `gen` (счётчик проходов), `first`,
  `lines []Line`, `shift`. Каждый `Line` хранит **текст, из которого он был
 lexed** — это основа защиты от устаревания.
- `Request()` (стр. 329) — мгновенный возврат; пропускает проход, если версия и
  диапазон уже покрыты.
- `run()` (стр. 358): ветка `relexPatch` — главный трюк, см. ниже.
- `relexPatch()` (стр. 571): сравнивает текст строк прежнего и нового прохода,
  находит первый расшившийся индекс `a` и хвостовой совпадающий `b`; стартует
  перелексинг на `back=16` строк выше `a`, расширяясь вверх (back *= 4) до
  строки **вне мультистрочного токена** (`prev[s-1].open`); ниже идёт до
  `settle=3` подряд строк с совпавшими токенами (`relexAhead=160,
  relexMargin=32`, стр. 526).
- Ключевое условие приёма: строки **выше** изменения должны выйти токен-в-токен
  как прежде (`wrong`-проверка, стр. 621), иначе проход отбрасывается и старт
  уходит выше. Если старт дошёл до 0 строки — патч `exact`.
- `Line(i, text)` (стр. 463): рисующий код получает токены строки только если
  `h.lines[j].Text == text` — **устаревшая раскраска физически не может попасть
  на чужой текст**; строка, тронутая нетривиальной правкой, рисуется plain.
- `adjust()` (стр. 484): дешёвая эвристика — сдвиг токенов строки при одной
  вставке/удалении внутри неё (общий префикс/суффикс; замена → nil → plain).
- Замер: правка в 6000-строчном Go-файле ≈ 0.7 ms против 170 ms полного
  прохода (docs/ARCHITECTURE.md, раздел Performance).

### П2. Undo как персистентное дерево — `cmd/mayoi/history.go` + библиотека mygo

- `mygo/ui/text_buffer.go:10` — буфер это «indexed, persistent tree» (персистентная
  верёвка `internal/rope`): правка копирует ограниченные чанки и пути дерева,
  не весь документ.
- `TextSnapshot` (`text_buffer.go:19`) = иммутабельный корень + номер версии;
  `Restore` (стр. ~60) adopt'ит корень за O(1).
- `history.go:53` — шаг истории это `histStep{snap ui.TextSnapshot, sel [2]int}`:
  хранить состояние «до правки» почти бесплатно, потому снимков можно держать
  `maxUndo=1000` (стр. 59) со срезкой хвоста (стр. 63–68).
- Группировка: печатный текст склеивается в один шаг до паузы
  `typingPause=1200ms`, сдвига каретки или правки от приложения (стр. 76–110,
  `observe()`); vim-insert группируется через `groupOpen/groupJoin` (стр. 34–50).
- История принадлежит документу, а не текстовому полю: все колонки с одним
  файлом делят текст и историю (docs/ARCHITECTURE.md, «Editing and undo»).

### П3. Стейджинг хунка без патчей — `cmd/mayoi/hunks.go`, `diffhunks.go`, `internal/git/git.go`

- `stageHunk()` (`hunks.go:184`): применить HEAD-хунок к индексу нельзя — индекс
  мог уже отличаться. Вместо этого:
  1. `r.Show("", path)` читает **текущий** индекс свежим `git show :0:path`
     (`git.go:305–312`);
  2. заново считается диф index→worktree (`linediff.Hunks(index, work)`);
  3. `overlapping()` (`hunks.go:213`) берёт только хунки, пересекающиеся с
     желаемым;
  4. `linediff.Apply(index, work, picked)` собирает **новый полный текст
     индекса**;
  5. запись целиком: `git hash-object -w --stdin --path` + `git update-index
     --add --cacheinfo mode,sha,path` (`git.go:371–383`, режим файла
     сохраняется из `ls-files -s`).
- Формула: «нет патча, который можно собрать, и нет fuzz, который может
  промахнуться» — целевое состояние пересчитывается и пишется целиком, а не
  диффом поверх возможно-устаревшей базы. Тот же путь в дифвью
  (`diffhunks.go:180–202`) и для unstage через `inverted()`.
- Отдельно: `revertHunk` (`hunks.go:157`) — откат хунка это правка документа
  (шаг undo), не git-операция.

### П4. Git только через CLI с безопасными флагами — `internal/git/git.go`

- `run()` (`git.go:72–103`): **каждый** вызов git получает env
  `GIT_TERMINAL_PROMPT=0, GIT_OPTIONAL_LOCKS=0, LC_ALL=C, GIT_EDITOR=true`
  и `GIT_SSH_COMMAND=ssh -oBatchMode=yes` (когда пользовательский не задан) —
  логин с промптом падает сразу вместо зависания (стр. 73–77).
- Статус читается фоном: после изменений дерева, сохранения, git-команды,
  фокуса окна и каждые 5 секунд; идентичный статус дедуплицируется
  `Status.Equal` (`git.go:181`) и дешёвые пересчёты не запускаются; каждые
  1.5s — только mtimes индекса/HEAD/FETCH_HEAD (docs/ARCHITECTURE.md, «Git»).
- Таймаутов на git нет (всё в фоновых горутинах UI); у ssh-коннекта
  `ConnectTimeout=15` (`internal/remote/conn.go:216`).

### Быстрые пункты

**5. Потоковые результаты поиска** — `cmd/mayoi/search.go`: у каждого поиска
номер `gen` (`search.go:88`, инкремент в `resetSearch` 146/160); фоновые
воркеры (до 8) пишут в батч, флаш каждые **60ms** (`search.go:276`), а
`takeResults` отбрасывает всё чужое: `if gen != s.gen { return }` (стр. 451–453).
Устаревшее никогда не доходит до UI.

**6. Remote-файлы как пути** — `internal/remote/path.go`: префикс `/ssh:host/path`
прозрачен для `filepath` (стр. 17–21, `Split/Is`); `internal/vfs` повторяет
`os`-функции, диспатча по `remote.Is()` (`vfs.go:23–34`); один ssh ControlMaster
на хост, BatchMode, команды — маленькие POSIX-скрипты через stdin.

## Часть 3. Решения

### П1. Инкрементальная переподсветка — **НЕ ПЕРЕНИМАТЬ**

Причины: у нас нет цикла «правка на каждом keystroke → перекраска кадра», ради
которого паттерн существует. Осевшие карточки TUI уже рендерятся один раз и
живут в row-кеше (`entry_cacheable` + `RowPack`); подсветка не на горячем пути.
Tree-sitter к тому же умеет **нативный** инкрементальный перепарс
(`parse_with` + old tree), так что «трюк Mayoi» (лексическая верификация
окрестности) был бы нужен только если мы захотим дешёвого перепарса lsp/graph
действий сразу после правки большого файла: сейчас это ~13.5ms на 2k-строчный
файл и ~187ms на 1MB один раз на версию файла — кеш `parse_cache.rs` уже
убирает повторные действия по тому же контенту.
Цена внедрения инкрементальности (отслеживать old tree + диапазоны правок
между тул-коллами): 8–16 ч, выгода < 200ms на редкий случай. Отложить до
профильных свидетельств.

### П2. Undo как персистентное дерево — **НЕ ПЕРЕНИМАТЬ** (без свидетельств)

Наш store решает другую задачу: якорение правок модели (hashline-теги,
provenance) и восстановление после дрейфа, а не интерактивный undo. Глубина 4
версии/путь достаточна, потому что (а) агент перечитывает файл между правками,
(б) откат на дальнюю версию в harness-среде делает git репозитория.
Верёвочная история на 1000 шагов — переписываение половины pa-edit
(store/session/режимы работают полными текстами): 16–24 ч, риск регрессий в
самом чувствительном к validations крейте, выигрыш только в гипотетическом
сценарии «агент испортил файл и хочет откатиться глубже 4 версий без git».
Опционально и только при свидетельствах: поднять `DEFAULT_MAX_VERSIONS_PER_PATH`
4→8 (0.5–1 ч с тестом и переоценкой 64MB-бюджета).

### П3. Стейджинг без патчей — **УЖЕ ЕСТЬ; перенять только приёмы на будущее**

Принцип «пересчитай целевое состояние и запиши его целиком; затем проверь,
что реально легло» у нас реализован на каждом уровне: движок строит полный
`after` (engine.rs:5–8), кеш чтений сбрасывается перед apply (files.rs:7–9),
после записи перечитывается диск и дрейф докладывается модели
(session.rs:342–350, 571–577). Git-стейджинга в тулах нет, поэтому конкретная
механика `hash-object`+`update-index` сейчас некуда встраивать. **Записать в
память: если когда-нибудь появится git-стейджинг/частичный откат — копировать
схему hunks.go:184 (fresh index read → recompute → overlap-filter → write
whole), а не применять патч.** Трудозатраты сейчас: 0 ч.

### П4. Безопасный git — **ПЕРЕНИМАТЬ (единственное конкретное изменение)**

1. **Починить опечатку** `GIT_TERMINAL_PROMPTS=0` → `GIT_TERMINAL_PROMPT=0`
   в `pa-core/src/tools/shell_utils.rs:67` + тест на стр. 122. Переменной
   `GIT_TERMINAL_PROMPTS` в git не существует — сегодня credential-промпт git
   в bash-туле не отключён этой строкой (спасают только отсутствие TTY и
   GIT_ASKPASS=true; это хрупко). Проверить паритет с TS-бинарём: если в
   TS-исходнике та же опечатка, это осознанное расхождение в пользу корректности
   (на провод не влияет). 0.5–1 ч.
2. **Закалить `run_git` в pa-graph** (`changes.rs:426–460`): добавить те же env
   `GIT_TERMINAL_PROMPT=0, GIT_OPTIONAL_LOCKS=0, GIT_EDITOR=true, LC_ALL=C`
   локально в `run_git`/`run_git_bytes` (pa-graph не может зависеть от pa-core —
   направление зависимостей; это ~10 строк в самом крейте). 1–2 ч с тестом.
3. Опционально: таймаут на `run_git` (spawn + poll + kill), 2–3 ч — у Mayoi
   таймаутов тоже нет (фоновые горутины), но у нас вызов висит на пути
   тул-колла графа. Делать вторым шагом, если измерится зависание.

Проверка «висящих git-промптов» в bash-туле после фикса: GIT_TERMINAL_PROMPT=0 +
GIT_ASKPASS=true (пустой вывод → мгновенный отказ) + SSH_ASKPASS_REQUIRE=never +
отсутствие TTY + kill группы по таймауту — покрытие adequate.

### 5. Стриминг результатов — **НЕ ПЕРЕНИМАТЬ** (эквивалент уже есть)

Отбрасывание устаревшего у нас структурное: порядок turn'а + abort
(`pa-agent/src/abort.rs`) + `result_partial`/финальный кадр. Счётчик поколений
нужен только при параллельных конкурирующих вычислениях одной выдачи — у нас
таких нет. 0 ч.

### 6. Remote-пути — **НЕ ПЕРЕНИМАТЬ**

Разные задачи: Mayoi — прозрачная удалённая ФС для редактора; наш
path_policy — диспетчеризация internal URL к host-ответам и запрет чужих URI
(path_policy.rs:65–90, 322+). Паттерн может пригодиться, только если в allspark
появятся ssh-работспейсы; тогда — префикс-путь + vfs-диспетчер как у них.
0 ч.

## Часть 4. Топ-1

**П4 (безопасный git) — единственный паттерн с конкретной, дешёвой и реальной
пользой прямо сейчас.** В нём найден настоящий дефект: опечатка
`GIT_TERMINAL_PROMPTS` обнуляет защиту от credential-промптов во всех
bash-порождениях git (строчка, которая должна работать, не работает никогда), и
`run_git` графа вообще без закалки. Суммарно ~2–3 ч, ноль архитектурных
изменений, закрывает класс «тул-колл завис навсегда» — ровно тот класс, против
которого Mayoi строил свой `run()`. Остальные три паттерна либо уже выражены в
нашей архитектуре в собственной форме (П3 — полностью, П1/П5 — эквивалентами),
либо решают проблемы интерактивного редактора, которых в harness-цикле нет (П2).
