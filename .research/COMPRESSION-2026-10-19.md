## 1. Методы компрессии: полный каталог и наш вердикт

### 1.1 Радикальная резка на новых моделях — ДА, но после A/B
Anthropic удалил **>80%** промпта Claude Code на Opus 5/Fable 5 без потери на
coding-эвалах. Оговорка: это «смена формы» (500+ условных кусков → суждение), и
относится к Claude 5 generation. Наши модели — GLM/DeepSeek/CodeBuddy → **сначала
абляция, потом резать**.

### 1.2 Правила → суждение — ДА, главный кандидат
«Never write comments» → «Write code that reads like the surrounding code». Жёсткие
правила конфликтуют между собой (system vs skills vs user) и заставляют модель думать
о конфликте. У нас `usage.md` = 31 императив «must», `opinionated.md` = 23 «guideline»
— пересечения с AGENTS.md и user-промптом гарантированы.

### 1.3 Примеры → дизайн интерфейса — ДА
Enum `pending/in_progress/completed` в схеме тула заменяет абзац инструкций.
Примеры на новых моделях **конструируют** их. Наш аналог — богатые схемы (уже есть).

### 1.4 Progressive disclosure (skills) — УЖЕ ЕСТЬ, но дорогой
Level 1 metadata ~100 tok/скилл, Level 2 SKILL.md <5k по триггеру, Level 3 — 0 до
чтения. У нас 48 скиллов × ~512 симв = **6 142 tok постоянно**. Claude Code рекомендует
**<10 workspace / ≤30 total**; наш cap 64 — выше. Действие: пересмотреть лимит вниз
(30) + cap описания 300 симв (−694 tok) + убрать `<location>` (−2.2k симв).

### 1.5 Progressive disclosure для тулов (`defer_loading`) — в бэклоге P3
Claude Code перенёс code review/verification в скиллы. У нас ростер детерминирован
(сортировка) — отложить до данных метрики инвалидации.

### 1.6 Дедупликация system↔tool — УЖЕ ХОРОШО
Замер: core↔usage — 13 общих 5-грамм (jaccard 0.007), остальные пары — 0. Явного
дубля мало; вес — не дубли, а объём.

### 1.7 Абляции вместо интуиции — ГЛАВНЫЙ ИНСТРУМЕНТ (P1)
Метод: разбить промпт на семантические компоненты, по очереди удалять, гонять
фиксированный eval. Классы: high-signal (ломает метрику) / low-signal / harmful
(улучшает удаление). Типичная находка — «2000-токенный документ, выросший за 6
месяцев, с тремя версиями "be concise"».
**Наш план**: 4 руки × N задач — (a) полный, (b) без usage.md, (c) без opinionated.md,
(d) usage+opinionated слиты в 1/2. Ожидание: usage.md (31 мандат, 1 482 tok) —
кандидат на harmful. Потолок: −2 100 tok из префикса.

### 1.8 Instruction saturation — МЫ В ЗОНЕ РИСКА
IFScale: 500 инструкций, 20 моделей → лучшее 68%; primacy-эффект пикует на
150–200 инструкциях, при 300+ все падают к ratio 1.0–1.5. У нас usage (31) +
opinionated (23) + 126 буллетов core ≈ **зона пика**. Порядок инструкций уже влияет.

### 1.9 Lost in the middle — НАШ usage.md В ХУДШЕЙ ПОЗИЦИИ
U-образная кривая: середина используется хуже краёв. `usage.md`/`opinionated.md`
(2 100 tok мандатов) сидят в **середине** статического префикса. Действие при
абляции: либо резать, либо переносить к краям.

### 1.10 Context rot / NoLiMa / RULER — фон
Деградация при росте входа даже на тривиальных задачах; 11 из 13 моделей на 32K
падают ниже 50% baseline. Довод против «сложить всё, что может пригодиться».

### 1.11 LongLLMLingua-стиль сжатие — ОСТОРОЖНО
+21.4% качества при ×4 меньше токенов — это про **retrieved-контекст**, не про
системный промпт с императивами. Переносится плохо.

### 1.12 Серверный context editing (Anthropic) — ОРИЕНТИР для compaction
+29% на agentic search, с memory tool +39%; −84% токенов на 100-turn eval.
Наш аналог — compaction: сверить политику с их подходом.

### 1.13 AGENTS.md: контекст ≠ способности — РЕЗАТЬ БЕЗОПАСНО
288 прогонов: стратегия инъекции **не меняет** pass rate (p=1.00/0.66), но
selective-инъекция снизила cache-creation на 11/11 (p=0.012), blind-запуски
3.67→1.67, wall-clock −24%. SWE-bench: context-файлы **снижают** success и
+20% стоимости; developer-provided +4%, LLM-generated −3%. Рекомендация: только
минимальные требования, без «обзоров репозитория». **Прямой аргумент за наш
project-context: только готчи.**

### 1.14 Формат: XML vs Markdown — НЕ ОПТИМИЗАЦИЯ КАЧЕСТВА
Прямой A/B на 12 моделях: XML-делимитеры не дали измеримого эффекта. Anthropic
рекомендует XML «для однозначности» — противоречие. Итог: XML — гигиена парсинга.
У нас `<available_skills>` XML — менять не надо.

### 1.15 Лимиты контекст-файлов — ДЕЛАЕМ
Cursor: <500 строк, split composable, reference не copy. Codex: 32 KiB бюджет
кумулятивный по цепочке (большой корневой AGENTS.md молча выбрасывает вложенный —
у нас контекст-файлы с лимитом 256 KiB каждый, но **кумулятивного бюджета нет** —
добавить). Copilot: «very long files may be overlooked».

### 1.16 Лимит числа скиллов — ПЕРЕСМОТРЕТЬ
Claude Code team-memory: <10 workspace, ≤30 total; сверх — в memory files.
Наш cap 64 — выше рекомендации. Согласовать с 1.4.

## 2. Конкретный план (по убыванию ценности)

### C.1 Абляционный прогон (P1, 1-2 дня)
4 руки × N qa-tasks (faux лейн): полный / −usage / −opinionated / usage+opinionated
слитые ½. Метрики: pass rate + cache-creation + стоимость. Артефакт: таблица
«секция → Δpass, Δtok». Без этого резать — гадание.

### C.2 Cap инвентаря скиллов (P1, 2-4ч)
MAX_SKILLS_INVENTORY 64 → 30 (Claude Code), cap описания 300 симв (−694 tok),
убрать `<location>` из записи (−2.2k симв). Итого −3-4k tok постоянного хвоста.

### C.3 Кумулятивный бюджет context-файлов (P1, 4ч)
Сейчас — лимит на файл (256 KiB), нет бюджета на сумму. Codex-паттерн: бюджет на
цепочку root→cwd с вытеснением дальних. Защита от «5 AGENTS.md по 200 KiB».

### C.4 Перенести tool-сигнатуры из core.md в схемы (P2, 4-8ч)
113 строк-сигнатур ≈ 10 809 симв (~2 700 tok) = 72% core.md. Anthropic: инструкции
по использованию — в description тула, не в system prompt. Экономия денег мала
(0.1× цена), но −25% статического префикса и меньше instruction saturation.
Делать после C.1 (абляция покажет, какая часть мёртвая).

### C.5 usage.md: правила → суждение (P2, 4-8ч, после C.1)
31 императив → сгруппировать в принципы («match surrounding style» вместо 5 запретов).
Если абляция покажет harmful — резать агрессивнее.

### C.6 project-context: только готчи (P2, 2-4ч)
AGENTS.md-класс: убрать «обзоры репозитория», оставить минимальные требования.
Скрипт-линтер на «обзорные» фразы — опционально.

## 5. АКАДЕМИЧЕСКИЕ МЕТОДЫ СЖАТИЯ (таксономия NAACL 2025) — что применимо на самом деле

Дополнение от пользователя (анализ вне моих прежних источников). Таксономия по
обзору [Prompt Compression for LLMs: A Survey](https://aclanthology.org/2025.naacl-long.368/):

### 5.1 Три класса методов

| Класс | Методы | Что жмёт | Наш вердикт |
|---|---|---|---|
| **Hard filtering** | Selective Context, LLMLingua, LongLLMLingua (question-aware), LLMLingua-2 (BERT-классификатор, latency до 2.9x ниже), TACO-RL | токены по перплексии/самоинформации | **НЕ для системного промпта** — ломает точные формулировки; ДЛЯ tool outputs и истории — да |
| **Paraphrasing** | Nano-Capsulator, CompAct | LLM переписывает короче | рискованнее extractive (−4.7 F1 на мульт文档 QA) — НЕ для инструкций |
| **Soft prompt** | Gist Tokens (26x), ICAE, AutoCompressor, 500xCompressor, xRAG/COCOM/LLoCO (RAG) | текст → скрытые KV-токены | только self-hosting + права на веса; у нас закрытые API — НЕДОСТУПНО |
| **Ручная реструктуризация** | аудит дублей, проза→списки, удаление устаревших | — | **БАЗОВАЯ ПРАКТИКА**: −20–40% без риска |

### 5.2 Почему hard-методы не работают на инструкциях агента

1. **Другой тип контента**: компрессия выигрывает на избыточном (RAG-доки, история);
   инструкции короткие, плотные, точная формулировка критична (порядок, запреты,
   формат вывода). Perception Compressor: на инструктивных сценариях LLMLingua и
   SelectiveContext проседают ХУЖЕ zero-shot. «Lost in Compression» (arXiv:2608.26175):
   hard-компрессоры системно теряют критичную для инструкций информацию.

2. **Плотность инструкций ≠ длина** (IFScale): ужатие плотного списка в короткий,
   но столь же плотный — не решает; нужно СНИЖЕНИЕ ПЛОТНОСТИ в контексте.

3. **Что реально съедает контекст у кодового агента** (Systima, Claude Code vs
   OpenCode): системный промпт ~6.5k/2k, **tool schemas ~24k/~4.8k**,
   `<system-reminder>` ~8k симв, 72KB AGENTS.md = +20k токенов, 5 MCP серверов
   +5-7k, субагенты умножают базу на каждый ход (4.2x при фанауте в двух).
   **Вывод: сжатие промпта у агента = сжатие tool-схем, инжекций и конфигов**,
   а не текста инструкций.

### 5.3 Что индустрия делает вместо компрессии

| Практика | Пример | Наш статус |
|---|---|---|
| **Agent Skills / progressive disclosure** — в контексте только каталог, полное содержимое по tool-вызову | Anthropic "Equipping agents for the real world"; инцидент Claude Code #45188: +70k токенов за 5 дней (каталог 47 скиллов целиком на каждый ход) → правки снизили 10.7k→6.7k | У НАС УЖЕ ЕСТЬ (native_tools_section + skills inventory), но наш инвентарь 6.1k tok — это их «до» |
| **Just-in-time контекст** — лёгкие идентификаторы сразу, содержимое по grep/glob | Claude Code | у нас — частично (read по требованию) |
| **Prompt caching** | −41-80% затрат, −13-31% TTFT | у нас есть (boundary на проводе) |
| **Compaction / tool-result clearing / structured notes** | Claude Code | compaction есть; **tool-result clearing** — в бэклоге (трек A.2) |
| **Gist tokens (Shopify Sidekick)** | 6000→1500 tok (4:1), KL-дистилляция, замороженные веса; TTFT −19%, latency −38%, −14% GPU при 350 RPM | НЕДОСТУПНО: закрытые API; единственный публичный прод-кейс soft-метода |
| **Минимальный «пол»** (OpenCode-стиль) | ~7k vs ~33k у Claude Code = 4.7x разница на уровне дизайна | наш пол ~7.5k + tools — уже ближе к OpenCode |

### 5.4 Сверка с нашим планом (COMPRESSION §2) — что меняется

| Пункт плана | Поправка от академической таксономии |
|---|---|
| C.1 Абляция 4 руки | **Остаётся** — ручная реструктуризация и есть «базовая практика»; абляция её направляет |
| C.2 Cap скиллов | **Усиливается** — это ровно Agent Skills/progressive disclosure, главный паттерн индустрии |
| C.3 Кумулятивный бюджет context-файлов | **Усиливается** (AGENTS.md 72KB = +20k токенов/запрос) |
| C.4 Сигнатуры в схемы | **Главный рычаг подтверждён**: tool schemas доминируют базу (~24k из 33k у CC) |
| C.5 usage.md правила→суждение | **Подтверждён** (Anthropic «right altitude», суждение вместо if-else) |
| C.6 project-context только готчи | **Подтверждён** (AGENTS.md = +20k токенов) |
| НОВОЕ: LLMLingua на tool outputs/историю | **Добавить в бэклог**: компрессия направляется на tool outputs и историю, НЕ на системный промпт |
| НОВОЕ: префикс и decode | **Учесть**: кэш не устраняет decode-стоимость — чтение KV растёт линейно с длиной префикса; значит компрессия префикса экономит не только деньги, но и latencydecode |

### 5.5 Итоговая формула для нашего форка

1. **Не применять** LLMLingua-семейство и paraphrasing к системному промпту —
   академически показано, что ломает инструкции.
2. **Применять к tool outputs и истории** — там избыточность есть (это и есть наш
   трек A.2 потолок + будущий tool-result clearing).
3. **Структурные методы — основной рычаг**: skills/progressive disclosure (есть,
   усилить cap'ами), минимальный ростер (есть, отсортирован), байт-стабильный
   префикс (есть, проверен тестом).
4. **Gist tokens — недоступны** на закрытых API; если когда-нибудь появится
   self-hosting OpenWeight-модели как первоклассный путь — переоценить.

### 5.6 Чек-лист «сжатие промпта» для кодового агента (финальный)

- [ ] Аудит дублей и устаревших правил (−20-40% базовая практика)
- [ ] Редко нужные инструкции → скиллы/файлы
- [ ] Обрезка/унификация tool-схем (наш largest lever: native_tools 5.9k)
- [ ] Контроль AGENTS.md/CLAUDE.md (кумулятивный бюджет, C.3)
- [ ] Байт-стабильный префикс для кэша (есть, тесты)
- [ ] Компрессия ТОЛЬКО для истории/tool outputs (LLMLingua-класс сюда можно)
- [ ] НЕ жать инструкции автоматически

## 5. ПОПРАВКА от анализа OpenCode issues: cap скиллов → байтовый бюджет + дельты

Анализ 5000 issue titles + чтение 10 key issues sst/opencode (см.
OPENCODE-ISSUES-2026-10-19.md) даёт три поправки к плану выше:

### 5.1 Cap скиллов по количеству → байтовый бюджет + репорт + lazy
OpenCode не режет по количеству: они делают запись дешёвой (одна строка,
отсортировано, дельты при изменениях) и тяжёлое прячут за тул `skill` (один
параметр id). Жёсткий cap молча прячет функциональность (#20647: 1539 скиллов =
580 KB / 147k tok → Bedrock 400). Наш cap 30 → заменить на:
- **байтовый бюджет инвентаря** (уже есть — MAX_SKILLS_INVENTORY_BYTES)
- **репорт обрезки** (уже есть — «more skill(s) not listed»)
- **ленивый тул** (содержимое по запросу — уже есть)
- cap 30 оставить как аварийный предохранитель, не как основной механизм.

### 5.2 LLMLingua НЕ для туловых выводов вообще
OpenCode нигде не «сжимает» выводы семантически — только структурная обрезка
head-keep + полный вывод в файл. Компакционный промпт требует сохранять точные
строки (пути, команды, ошибки) — LLMLingua портит именно это; модель получает
изменённые идентификаторы кода. Если сжимать — только прозу (логи обсуждений),
никогда код/диффы. Базовый механизм — их: лимиты + файл + маркер с путём.

### 5.3 Новый пункт плана: протокол «baseline + дельты» (16-24ч, P1)
Отсутствующий у нас примитив — ядро V2 OpenCode (instructions/index.ts:26-45,
instruction-state.ts:45-47). Все источники инструкций (AGENTS.md, skills, MCP,
дата, env) НЕ в system-блоке, а как append-only delta-сообщения поверх frozen
baseline. Key+hash dedup, initial/changed/removed, re-inject после компакции,
ordering most→least shared ради кэш-префикса. Это то, что заставляет их префикс
быть байт-стабильным при изменении любого источника — у нас любое изменение
AGENTS.md/скилла/MCP инвалидирует весь prefix.

### 5.4 Ещё 4 пункта из их грабель (все в бэклог)
- **Root-derived cache key** для форков/сабагентов (2-4ч; их #55243 — fork-of-fork
  шлёт чужой key, полный re-prefill; у нас subagent spawn — та же ошибка вероятна)
- **Guardrails компакции** (10-14ч; их #54993/#56350/#56784 — 6+ багов одного класса):
  суммаризатор без тулов, бюджет от сессионной модели, «Continue» только при
  tool-calls, запрет пересказа статического контента
- **Маркер обрезки вывода с путём к файлу** (4-6ч; их #11313 — re-run-лупы без него)
- **Wire-тесты конвертера схем** (их #4357/#11357 — union types / inline refs
  теряются у специфичных провайдеров)

### 5.5 Обновлённый первый срез (30-46ч, P1)
п.5.3 протокол дельт + перенос AGENTS.md/env/даты в него + маркер обрезки +
cache-key lineage. Это даёт наибольшую экономию на кэше при минимальном риске;
компакция — вторым срезом, Code Mode — третьим.
