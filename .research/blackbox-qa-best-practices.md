### 1.5. Детерминизм и честная статистика

- **pass@k vs pass^k** (Anthropic): pass^k = вероятность, что **все** k триалов успешны; при per-trial 75% и k=3 pass^k ≈ 42%. Для регрессий консистентности (наш случай) — pass^k, k=3–5.
- Изоляция триала: чистое окружение на прогон (остаточные файлы/кэш/git-история предыдущих триалов = коррелированные фейлы и накрутка).
- **Pairwise A/B + статистика**: bootstrap-CI (≈1000 ресемплов) на разностях; разности <30 Elo-очков требуют сотен сравнений — для двух фиксированных версий дешевле прямой знаковый/биномиальный тест на парах; активный сэмплинг «похожих» пар режет стоимость вдвое. https://mbrenndoerfer.com/writing/preference-evaluation-pairwise-comparisons-elo-llm
- Судья: temperature=0, ротация позиций (A/B/B/A) против position bias, декомпозиция рубрик на дискретные чеки, калибровка против человека (inter-rater agreement), «Unknown» как разрешённый выход против галлюцинаций: https://www.openlayer.com/blog/llm-as-judge-evaluation-guide, https://arxiv.org/html/2506.22316v2, https://futureagi.com/blog/llm-as-judge-best-practices-2026/, https://www.braintrust.dev/articles/what-is-llm-as-judge

### 1.6. Контроль дрейфа судьи (критично для нашего jev-слоя)

- **Frozen anchor set** (метод): версионируемый набор задач с человеческими метками; старый и кандидат-судья прогоняются на идентичных входах; меряем **label flips** и **calibration error по слайсам**; приемка судьи блокируется при нарушении предекларированного допуска; средний скор — НЕ достаточная метрика. URL: https://qaskills.sh/blog/llm-eval-judge-model-drift-detection (+ LinkedIn-заметка Layerlens)
- **Манифест прогона**: каждый результат отвечает «какой judge bundle, на каком датасете, против какого rubric и какой сборки»: `{datasetRevision, rubricRevision, judgePromptRevision, parserRevision, candidateBuild, purpose}` — сравнимость истории.
- **«Who Drifted: the System or the Judge?»** (arXiv:2606.15474, 2026): anytime-valid/sequential-тест различает дрейф системы от дрейфа судьи; дешёвый монитор скорит каждую интеракцию, эскалация при дрейфе скор-распределения.
- Dataset debt: если ревьюеры регулярно опрокидывают старые якоря — нужна новая adjudicated-версия датасета; исторические метрики остаются привязанными к старой версии якоря (не пересчитываются молча).

### 1.7. Real-world task mining

- Источники задач: bug-трекер, support-queue, прод-трейсы, ручные проверки перед релизом (Anthropic Step 1); «convert traces to evals» (Redis).
- Качество задачи: два доменных эксперта независимо сходятся в вердикте; **reference solution обязателен** (доказывает решаемость и корректность грейдеров); 0% pass@100 = сломанная задача, а не тупой агент (Anthropic).
- Баланс: тестировать и «должно произойти», и «не должно» (односторонний сьют → односторонняя оптимизация: агент начнёт искать всегда/никогда).
- Специфика TUI/CLI: Terminal-Bench-модель (Docker-песочница + pytest-оракул на состояние среды); tmux/pty-запись (asciinema cast) как воспроизводимое доказательство прогона: https://github.com/asciinema/asciinema (Rust-реализация), наши tmux-харнессы — готовая база.

## 2. Что такое «agentic-qa» и его применимость

Термин указывает минимум на два разных проекта — важно их различать:

1. **`partarstu/agentic-qa-framework` (QuAIA™)** — https://github.com/partarstu/agentic-qa-framework (AGPL-3.0, 33★).
   Это **агенты ДЛЯ тестирования обычного ПО**: ревью требований, генерация тест-кейсов, UI/API-исполнение, отчёты; Jira/Confluence RAG, оркестратор A2A, мониторинг агентов.
   **Применимость к нам: низкая.** Это про автоматизацию QA-жизненного цикла агентами, а не про чёрно-ящичное тестирование самих агентов. Перенимать нечего, кроме идеи «состояния агентов AVAILABLE/BUSY/BROKEN + автоматическое восстановление» для нашего QA-раннера.
2. **`makieali/agentswing`** — https://github.com/makieali/agentswing (MIT, новый, 2026).
   «Black-box QA for AI agents»: наводишь на любой endpoint (n8n, webhook, свой API), описываешь персоны и цели; фреймворк ведёт **реальные многоходовые диалоги** как симулированный пользователь, скорит (LLM-as-judge + ассерты), репортит что сломалось. No SDK / no instrumentation — чистый чёрный ящик. Ключевые идеи, переносимые к нам:
   - **персоны + цели + ожидания** как формат сценария;
   - ассерты поверх диалога (JSONPath и пр.);
   - **калибровка судьи как отдельный процесс** (`calibrating-the-judge` скилл: «можно ли доверять судье»);
   - дистрибуция экспертизы через markdown-скиллы (Q&A по троблшутингу);
   - тестовый ключ ≠ ключ агента (судья и «пользователь» живут отдельно от тестируемой системы).
   Сам инструмент заточен под HTTP/chat-эндпоинты — для TUI-агента не годится напрямую, но архитектурная рамка (persona→dialog→judge→calibration) переносится один в один.
3. Также в выдаче фигурируют платформы «Agentic QA» (Sorify и др.) — коммерческие E2E-платформы для веб-агентов; вне нашего фокуса.

**Вывод:** как «проект» agentic-qa (QuAIA) нам почти бесполезен; как **подход** (black-box, persona-driven, judge+calibration — agentswing-паттерн) — полезен и вошёл в архитектуру ниже.

## 3. Применимое к НАМ: архитектура «Real-Task Deviation Suite» для allspark

Цель: между двумя сборками форка / двумя наборами настроек / двумя моделями — отличить **реальную поведенческую деградацию** от шума, снаружи системы (без instrumentation), на реальных задачах, дёшево.

Готовые активы, на которые опираемся: append-only JSONL-транскрипты сессий (сырец для трейс-ассертов и судьи), tmux-харнесс, headless-планы, differential-инфраструктура.

### Уровень 0 — Захват и версионируемость (базис, уже почти есть)

- Каждый прогон сьюта пишет полный транскрипт (messages + tool calls + timing) в JSONL — формат унифицирован с сессионным.
- Манифест прогона: `{suiteRev (git rev корпуса), binaryBuild (fork.NNN), modelId@provider, settingsHash, judgeBundle, seedPolicy, purpose}`. Без манифеста сравнение версий недействительно.
- «Prompt + model id = релизный артефакт»: смена системного промпта = релиз, проходит те же гейты.

### Уровень 1 — Детерминированные задачи-оракулы (smoke-tier, CI-гейт)

- **Корпус**: `qa-tasks/` git-репозиторий (или каталог в моно-репо), задача = каталог: `task.yaml {id, difficulty, budget(токены/время/шаги), setup.sh, prompt, oracle, reference-solution/}`.
- **Оракулы** (по Anthropic YAML-схеме): `deterministic_tests` (pytest/shell-проверки артефактов — Terminal-Bench-паттерн: проверяем **состояние среды**, не текст), `state_check` (τ-bench: сравнение финального состояния — файлы/settings/JSON-wire), `static_analysis`. Никаких оракулов на точную формулировку ответа.
- **Старт**: 20–50 коротких задач из реальных фейлов (issue-трекер форка + ручные проверки перед релизом + инциденты сессий). Каждой задаче — reference solution (решаемость + корректность оракула). Баланс «должен/не должен» (например: должен использовать скилл / не должен звать сеть; должен спросить подтверждение / не должен зацикливаться).
- **Изоляция**: каждый триал в чистом temp-окружении (tmp HOME как в allspark-изоляции, свежий git-репозиторий задачи, pinned зависимости, network-off по умолчанию). Никаких остатков предыдущих триалов.
- **Метрика регрессии**: **pass^3** на задачу (все 3 триала), для capability — pass@1. Гейт: pass^3-фейл на задаче, которая в baseline была стабильной (pass^3 зелёная в ≥2 последних прогонах) = red. Новый фейл нестабильной задачи = yellow (требует судью уровня 3).
- **Стоимость**: 15–20 задач × 3 триала против дешёвой модели (или через кэширующий провайдер) — цель <15 мин CI; полный корпус — nightly.
- **Порогование**: гейт не «весь сьют упал», а дельта: −3 п.п. task-completion или ≥2 стабильные задачи потеряли pass^3 → блок (Sentrial-подход, пороги предекларированы).

### Уровень 2 — Trace-ассерты и поведенческий фингерпринт (дёшево, без LLM)

- **Мягкие инварианты траектории** (не жёсткая последовательность!): обязательные вызовы (сделал `edit`, не `bash sed`), запрещённые (сеть при network-off, `rm -rf` вне tmp), бюджетные лимиты (шаги/токены/время/число подагентов), harmful-call rate = 0, retry-паттерны (не >N повторов одного tool-call подряд).
- **Фингерпринт сьюта**: вектор {частоты инструментов, медианные шаги на задачу, доля задач с subagent-использованием, доля отмен, p95 латентности триала}. Регрессия = дельта против baseline-вектора (манифест-привязанного), порог по компонентам. Ловит деградации, невидимые оракулам уровня 1 («агент стал звать bash вместо edit», «перестал пользоваться скиллами», «разрослась многословность»).
- Опционально CORE-метрики (Path Correctness через Levenshtein по последовательности `tool + канонизированные аргументы` против reference-решения) — как advisor-метрика, не гейт (шумно для мульти-путевых задач).
- Реализация: чистый Rust/Python-парсер наших JSONL — ноль затрат на LLM.

### Уровень 3 — Judge A/B сравнение версий (nightly + по-требованию)

- **Вход**: пары транскриптов (baseline vs candidate) на одной задаче/сценарии. Персона-сценарии agentswing-формата: {пользователь, цель, ожидания, «что должно произойти / чего не должно»}.
- **Судья**: один judge-call на одно измерение (декомпозиция рубрик), temperature=0, ротация позиций (A-then-B и B-then-A), обязательный выход `Unknown` → пара исключается из статистики. Span-level вопросы («правильный ли инструмент на шаге N») + trace-level («цель достигнута»).
- **Статистика**: знаковый тест на парах + bootstrap-CI на разности скоров; порог регрессии предекларирован в сьюте (например: ≥10% пар «candidate хуже» при p<0.05 → red). Elo не нужен (две фиксированные версии, не лидерборд).
- **Стоимость**: судья только на «yellow»-кейсы уровня 1 + на nightly-дифф полного корпуса + на изменения промптов/настроек. Пары «похожих» версий активнее не сэмплим — у нас фикс. набор.

### Уровень 4 — Контроль дрейфа судьи (jev-слой, обязателен)

- **Anchor set**: 100–200 замороженных транскриптов с человеческими вердиктами (адьюдикация спорных — ревью двух людей). Прогон нового judge-бандла (судья-модель/промпт/рубрика/парсер) против якорей: label-flip rate и calibration error по слайсам; допуск предекларирован (напр. flip ≤5%, по safety-слайсу = 0).
- **Anytime-valid мониторинг** (arXiv:2606.15474): последовательный тест «дрейнул судья или система» на потоке прогонов; эскалация человеку при срабатывании, а не после релиза.
- Каждая смена судьи = релиз с манифестом; исторические вердикты не пересчитываются молча.

### TUI-специфика

- Расширяем существующие tmux-тесты до **canary-задач против реальной модели**: tmux-сценарий (send-keys/ждать готовности экрана) на 3–5 ключевых user-visible инвариантах из AGENTS.md (например: `/compact` показывает started+completed, refinement показывает decoration) — но на живой сессии, не на mock-демоне. Сравнение — по критическим экранам (frame-diff уже умеем), не по полному cast.
- Полная запись прогона — asciinema cast (pty-recording) как артефакт-доказательство для ревью деградаций (attach к отчёту, не гейт).

### Что НЕ делать (анти-паттерны из источников)

- Жёсткие ассерты на точную последовательность tool-calls (Anthropic: хрупко, наказывает валидные пути).
- Оракулы на точный текст ответа (стринг-матчинг — не сигнал качества).
- Один LLM-судья на все измерения сразу; судья без «Unknown»; судья без ротации позиций.
- Средний скор как единственная метрика дрейфа судьи.
- Молчаливый пересчёт истории при смене судьи/датасета.
- Smoke-гейт длиннее ~15 минут или с model-graded ассертами внутри блокирующего тира.

## 4. Топ-5 рекомендаций (приоритет / усилие)

1. **[P0, S, 1–2 недели] Смоук-сьют уровня 1**: 15–20 детерминированных задач с оракулами состояния среды, выведенных из реальных фейлов (issue-трекер + ручные pre-release чеки), каждая с reference-solution; метрика pass^3; изоляция tmp-HOME; порог −3 п.п. / потеря 2 стабильных задач = блок. Это самый дешёвый и немедленный закрытель пробела; гонять против дешёвой модели в CI.
2. **[P0, S, ~1 неделя] Trace-инварианты + фингерпринт уровня 2** поверх уже существующих JSONL-транскриптов: обязательные/запрещённые действия, бюджеты, harmful-call=0, вектор поведения + дельта-порог против baseline-манифеста. Без LLM, без новых зависимостей; ловит именно «тихие» поведенческие деградации.
3. **[P1, M, 1–2 недели] Judge A/B-гейт уровня 3**: парное сравнение baseline vs candidate (rotation, t=0, Unknown-out, один чек на вызов), знаковый тест + bootstrap-CI, предекларированный порог; nightly против полной модели; персона-сценарии agentswing-формата для multi-turn поведения (многоходовые «разговоры» с агентом).
4. **[P1, S, 3–5 дней] Judge-drift контроль (jev-слой)**: замороженный anchor set с человеческими метками, приёмка judge-бандлов по label-flip/calibration-error, манифесты во всех артефактах; далее anytime-valid мониторинг по arXiv:2606.15474.
5. **[P2, M, 1–2 недели, периодически] Task-mining конвейер**: баг-трекер/поддержка/прод-трейсы → дистилляция задач (LLM-ассистированный черновик, обязательная человеческая валидация «два эксперта сходятся», reference solution, баланс должен/не-должен); пополнение сьюта = PR в корпус с ревью; пере-адьюдикация якорей при dataset debt.

Последовательность: 1→2 закрывают «видимые» регрессии за считанные дни; 3→4 добавляют статистически честное сравнение поведения и защиту от лжи судьи; 5 делает сьют живым. Совокупно это «Swiss-cheese»-модель Anthropic: ни один слой не ловит всё, слои перекрывают дыры друг друга.
