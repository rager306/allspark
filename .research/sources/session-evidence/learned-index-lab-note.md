# Learned Index Lab: PGM In Rust With Epsilon Guarantees

Обновление 2026-10-19. Два независимых прохода: исходники лаборатории и вторичные индексы kutha. Предыдущая заметка от 2026-10-17 описывала crates.io 0.1.1 и ставила kutha 9/10. С тех пор крейт стал 0.2.0, а открытие kutha восстанавливает теплоту lease через `set_index_mode`.

## Что в коде, а не в README

HEAD `2247c04` (2026-10-18), крейт `learned_index_lab` 0.2.0, edition 2024, лицензия Apache-2.0, зависимостей нет. `#![no_std]` нет: используются `std`, `Vec`, `f64`. Файлы: `src/lib.rs`, `src/pgm.rs`, `src/main.rs`. Нет `benches/`, `tests/`, `examples/`, CHANGELOG. CI гоняет check/test/clippy/fmt и не запускает release-бенч.

Реализован один алгоритм: статический жадный коридор наклонов по отсортированному `Vec<u64>`. Сегмент — `key`, `slope`, `intercept` (24 байта). Поиск: бинарный поиск сегмента, предсказание позиции, окно `[pos−ε, pos+ε]`, точное сравнение внутри окна. Это не рекурсивный и не динамический PGM Ферраджины–Винчигуэрры. Вставки, удаления, обобщённые ключи, payload и SIMD в дереве отсутствуют; шаблон issue сам относит dynamic inserts и multi-level PGM к будущей работе.

Публичный API: `build(data, ε)`, `find`, `lower_bound`, `range`, `memory_footprint_bytes`, `index_only_bytes`. Поля структуры публичные: снаружи можно сломать инвариант. `ε ≥ 1` проверяется всегда. Сортировка входа — только `debug_assert`: release проиндексирует неотсортированный массив молча.

## Гарантии, которые код держит

Ошибка — про позицию, не про приближённый ответ. На уникальных ключах окно плюс `binary_search` даёт точное да/нет, если предсказание не выпало из окна. `find` не откатывается на весь массив: ложное «нет» возможно. `lower_bound` и `range` при неясном окне сканируют весь вектор, поэтому заявленная сложность `O(log S + log ε)` не всегда верна.

Дубликаты: проба на 10 000 одинаковых ключей при `ε=2` держала ошибку 2 на своём сегменте, но `binary_search_by_key` по одинаковым `Segment.key` выбирал чужой сегмент (`lookup_max=9999`). `find` среди равных ключей возвращает любой индекс.

`f64` не годится как шаг источника истины и как вход отпечатка. Для lease это допустимо, если рядом есть точный fallback.

## Бенч README против харнесса

`src/main.rs`: N=1 000 000, 100 000 запросов, 10 прогонов, три распределения, `ε` 32 или 16. Базы: `BTreeMap` и `slice::binary_search`. Память BTree в печати зашита строкой «45.78 MB», не измерена. `black_box` нет. Цифры README (плотный hit ~63 нс, индекс 3.1 KB, 83 сегмента) — снимок чужой машины, не артефакт CI.

Плотный «miss» почти всегда меньше минимального ключа (на пробе N=1e5 — 99.9%). Ранний выход за два сравнения, а не отсев ключа внутри диапазона. «Index-only 3.1 KB» не включает копию ключей на 8 MB, которую `PgmIndex` владеет. Окно `ε=32` — около 9 кэш-линий, не 4, как написано в README.

## Kutha сейчас

Лог событий остаётся источником истины. Карты фолда — сбрасываемые lease. Соты Proposed. HNSW и Cypher не разморожены.

На `GraphFold` ровно два `BTreeMap`: `vt_by_from: BTreeMap<u64, Vec<usize>>` (valid-from → несколько фактов) и `tt_anchors: BTreeMap<u64, u64>`. Остальные горячие карты — хеш (`facts_by_relation` по `TermId`, пины по строке). `policy_by_ingest` — вектор, не дерево.

`as_of` / `live_at` при тёплом режиме идут через `vt_by_from.range(..=vt)`. `as_known_on` берёт предшественника в `tt_anchors`, затем `known_at` всё равно сканирует все факты. `admission.rs` по-прежнему смотрит `tt_anchors.last_key_value()` только чтобы отвергнуть неубывающий `TtAnchor`, это не путь `as_of`.

Eager на каждый push обновляет BTree. Этот крейт вставлять не умеет. Lazy и открытие снимка уже разделены: `finish_open` вызывает `set_index_mode`, чтобы ленивый снимок остался холодным сканом, а eager — тёплым диапазоном (`store.rs`, M106). Заметка 2026-10-17 про «открытие не вызывает set_index_mode» больше не верна.

Ключи `vt_by_from` — годы-`u64`, не UUID v7. UUID v7 — это `EventId` в хеш-картах. Масштаб в дереве: бенч по умолчанию N=10000, цель в заметке бенча 1e6. Живого корпуса «10⁴–10⁵ событий» в коде нет. Сдача сейчас `L_delivery=M106-closed`, не M104.

PGM не заменяет интервальный `as_of`: живость всё равно проверяется по каждому факту после отбора по `valid_from`.

## Что улучшает сейчас и что только потом

Сейчас, без нового Accepted и без разморозки HNSW:

- Lease на запечатанном сегменте лога: отсортированный столбец `u64` (смещение, время, хеш ключа доставки) плюс таблица локаторов. Сброс lease не трогает лог. Тот же слот, что неподключённый `SegmentIndex`.
- Всегда точный fallback, как у `lower_bound` лаборатории, не доверчивый `find`.
- После полной перестройки горячих карт можно мерить PGM как второй локатор по ключам `vt_by_from`. Постинг-списки `Vec<usize>` остаются. Eager-вставки в BTree не трогать.
- `tt_anchors` имеет смысл переводить на PGM только если карта станет большой. Сейчас это предшественник на коротком дереве.
- Плотные `TermId` 0..n уже O(1). PGM там не нужен.
- Чужой бенч не принимать: промахи внутри диапазона, `slice::binary_search` как честная база, измеренная память.

Потом, если замер на 1e6 покажет боль:

- Динамический PGM на пути записи. Этого крейта для этого нет, и это спорит с «лог дописывается, lease перестраивается».
- Рекурсивный PGM, когда сегментов много.
- Целочисленный PLA, если lease должен быть побитово стабилен.
- Двувременной интервал и Retract/Correct. Одномерный CDF ключей это не закрывает.

## Оценки

- kutha-graph: было 9/10 по форме ключей. Сейчас 6/10: lease совпадает с D5/D011/D040, API лаборатории не покрывает Eager, мультимап и `as_known_on`. Позже 8/10, если спайк на запечатанном столбце с fallback обгонит `BTreeMap::range` на целевом N=1e6.
- law-nexus: 6/10 без повторного аудита кода. Идея ε на структурных ключах жива; встраивать рано, пока нет своего корпуса.
- prime-agent: 3/10 без повторного аудита. Индексами владеет SQLite; объёмы малы.
