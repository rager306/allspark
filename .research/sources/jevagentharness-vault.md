# JevAgentHarness: Decision Models делят контроль с LLM

Первая систематическая работа о том, как харнесс агента может **делегировать routine-выборы** decision-модели (та самая Jev — 28% времени и 2.6% цены LLM-вызова) без потери успеха. UIUC + Princeton + Google, код обещан открытым (репо существует, 19★).

## Каркас: 8 точек × 5 режимов × 3 уровня

- **Decision points (8)**: три выбирают действие — tool, arguments, action (без tools); пять управляют петлёй — write memory, reflect, stop, route (на дешёвый LLM), read back заметки
- **Integration modes (5)**: Replace (модель всегда решает), Assist (шортлист для LLM), Guard (одобрить/отклонить выбор LLM), **Cascade** (модель отвечает первой, харнесс берёт ответ только при c(s) ≥ τ; иначе LLM), Trigger (решает, запускать ли опциональный шаг — reflection)
- **Уровни бенча**: L1 изолированные вопросы (BFCL v4 1114+1949, When2Call 928), L2 шаг-уровень на записанных прогонах (5314 состояний, ответ только скорится), L3 живой агент (тау²-bench, ALFWorld, mini-SWE-agent, SWE-agent, pi; DecisionGym — своя симуляция CS-деска с 68 tool и answer key на каждом достижимом состоянии, включая после ошибок)

## Главные числа

- Лучшая на изолированных вопросах модель решает лишь **69.5%** агентских задач — L1-скор не предсказывает L3
- Делегирование tool-choice **без фиттнутого порога: −19.0 п.** успеха; фиксированный порог 0.5: −21.5; **фиттнутый в shadow-режиме: −0.0 п. и −14.2% цены**
- Jev взял 27.2% tool-выборов и 20.8% аргументных при Flash — ни одна из 500 задач не изменила исход; с Flash-Lite порог оставил все выборы LLM (сэкономил ноль) — честный негативный результат
- Deploy AgentDecision-4B (свой GPU): −86.3% цены, 2.5x быстрее, без потери ≥3 п.; медиана ответа 31ms против 809ms Flash; 99.9% tool-выборов, 75.0% аргументных, −4.5 LLM-вызова/задачу
- **Coding-агенты — мало**: только route (strong/fast LLM на шаг) даёт 7.0–10.5%, надёжной экономии нет — у free-text действий decision-модель не отличает читающие шаги

## Формула порога (ядро метода)

`c(s) ≥ q_L − ΔC/V`: уверенность ≥ (точность LLM на этом выборе) − (цена сэкономленного вызова)/(цена неверного выбора, у них $1/задача). Фиттится на **shadow-траекториях самого агента** (150 калибровочных задач): q_L per decision point, ΔC, V, и калибровочная кривая модели. С Jev+Flash вышло **τ=1.00 для tools, 0.99 для args** — на деле пропускаются лишь почти верные ответы. Пороги перефиттятся при смене LLM, модели или правил задач.

## AgentDecision-4B: рецепт

API-модель не учит правил харнесса и не видела **состояний после собственных ошибок агента** (30.9% train-состояний — после ошибки; scripted policy специально повторяет ошибки разработки). Qwen3-4B + LoRA r=32: **SFT** на 15,694 visited states, таргет = α·one-hot + (1−α)·p_Jev, α=0.3, кросс-энтропия + Brier-член (μ=0.5) для калибровки — 2.2 GPU-часа. **GRPO в петле агента добавил ноль измеримого** (4.5 GPU-часа + $26.53 впустую); без SFT GRPO бесполезен (11.5% против 13.5%). Дальше публичные tool-use данные подняли L1 (78.8→85.1) но уронили L3 shifted (96.0→91.5) — специализация важнее универсальности. На shifted-задачах 4B обогнал учителя: 91.5% против Jev 82.0%; на must-ask состояниях Jev ошибался в 41.6% (58.3 точность), рецепт StartLux-4B дал 100%.

## Где делегирование ломается

1. **Необратимый неверный выбор** — все 34 провала Jev начались с него (cancel там, где надо было спросить); обученная на состояниях 4B не сделала ни одного
2. **Новое правило** (Hard-задачи): без перефита порога/дообучения агент решает 3.0% против 88.0% у LLM — рефит порога вернул успех Jev
3. **Guard'ы почти не экономят** (вызов LLM всё равно нужен); stop-guard принял 40.7% неверных остановок LLM — «decision-model guard никогда не должен быть единственным контролем необратимого действия»; адаптеры «контролируют цену и скорость, не security boundary»

# Применимость к prime-agent (форк allspark)

**9/10 — это буквально недостающий слой поверх существующего jev-judge.**

1. **Shadow-режим jev-judge уже есть — не хватает шагов 2–4.** Процедура статьи: (1) тихая запись на калибровке → (2) порог на каждую decision point → (3) тест каждой делегации «не хуже И дешевле» → (4) селект и фриз. Сегодня jev-judge делает (1) как бинарный арбитр сессий; статья даёт blueprint апгрейда: фиттить per-choice пороги на собственных траекториях сессий и продвигать делегации по одной, а не переключать бэкенд целиком (сейчас: typesafe→openrouter→subq)
2. **Валидация осторожности**: −19.0 п. без порога = дисциплина shadow-first правильная; формула c(s) ≥ q_L − ΔC/V и калибровочная кривая — конкретика, которой не хватало
3. **Таксономия 8×5 — чек-лист точек внедрения в RLM-петлю**: tool-choice cascade (у allspark фиксированный набор tool — выбор это честный multiple-choice), args cascade (fixed-list аргументы), reflect trigger, stop guard (осторожно: 40.7% неверных стопов), route для суб-агентов
4. **Необратимые действия — никогда не делегировать** (все 34 провала; guard ≠ security boundary) — ложится на существующую цепь voi → pa-jev → человек: decision layer только для цены, эскалация человека остаётся
5. **Coding-агенты экономят мало** (7–10.5% только на routing) — prime-agent как coding-агент не получит 86%; честные ожидания
6. **Если когда-нибудь учить локальную decision-модель**: SFT на собственных visited states (с ошибками!) с Brier-калибровкой, GRPO пропускать; но это heavy — пока держать в голове
7. **Дрейф-мониторинг**: доля ответов выше порога — сигнал для рефита; прямой аналог для jev-judge — трекить agreement-rate на сессиях

Свежая волна: OpenJev, Intern-Decision, StartLux-Decision, DecisionFlow, REFLEX (глобальный порог против их per-point) — рынок decision-слоя растёт, статья задаёт ему методологию измерений.
