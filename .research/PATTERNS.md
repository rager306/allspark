## Принципы Prime

1. Модель не обязана держать всё в тексте: persistent Python REPL служит рабочей памятью и средой программной оркестрации (RLM/PTC).
2. Агентные сессии — supervised workers, дочерние агенты — настоящие независимые сессии. Изоляция жизненного цикла не равна sandbox.
3. Continual harness хранит и корректирует правила/память/skills/specs; изменения имеют историю и rollback. Это уже learning substrate, но не автоматически доказанное обучение предпочтениям.
4. Factory — уже state-machine/DAG с guards, joins, retries, budgets. Runtime state factory не переживает kernel restart; дети переживают. Сохранение задач != сохранение оркестрации.
5. Provider context — построенное представление session history. Compaction, recent tail, anchors и full-output artifacts уже существуют. Требуется сравнить точную семантику selective fold/recall, а не объявлять историю потерянной.

## Рекомендуемые паттерны

### 1. Обучение предпочтениям через отдельную проверку сигнала (Command Code Taste)

Цепочка: человеческое исправление/accept/reject/edit -> извлечение кандидата -> оценка реальное предпочтение/шум, область, противоречия -> читаемое правило -> применение к релевантной задаче -> проверка на новых задачах.

Ключевое разделение: модель, которая красиво сформулировала урок, не должна сама объявлять его верным и глобальным. Одобрение всего patch — слабое свидетельство предпочтения каждой строки; прямое исправление пользователя — сильнее. Несколько пересказов одного источника не независимые подтверждения. Противоречие может означать другую область действия, а не смену вкуса.

В Prime частично есть: scoped harness, refine, evidence/history/rollback. Дополнение — качество допуска, отрицательные сигналы, область проекта/пользователя, активное пересмотрение уверенности. Защита refine от одновременного перезаписывания не является разрешением смысловых противоречий предпочтений.

Эффект: меньше повторных исправлений пользователя и навязанных выдуманных правил. Проверка: новые задачи с ранее не показанными исправлениями, слепое сравнение пользователем, доля ошибочных правил и объём ручной доработки. Passing tests не проверяет taste. Документация Command Code описывает taste-1 как decision model, но calibration/RL/кратные ускорения независимо не проверены.

### 2. Независимый наблюдатель с дозированной обратной связью (oh-my-pi Advisor)

У советника свой контекст, свои наблюдения, отдельный канал замечаний и ограниченная власть. Разделить выполнение и проверку; читать изменения/дельты, проверять факты, выдавать nit/concern/blocker, удалять повторы и не перебивать исполнителя по мелочам. Ошибочная рекомендация не должна автоматически становиться командой.

В Prime есть children, messaging, resident factory states; это делает возможным паттерн, но не равнозначно готовому advisor с cadence/dedup/severity/backlog policy.

Эффект: ловить пропущенные ограничения и ложное «готово» прежде пользователя. Проверка: исторические провалы, ложные блокировки, предотвращённая доработка, добавленные время/стоимость. Не включать ревью каждого шага по умолчанию; проверять границы плана/патча/итогового ответа. Read-only инструкция сама по себе не обеспечивает ограничение прав.

### 3. Завершение определяется доказательством, а продолжение — сохранённым состоянием (GSD Core/Path + RuFlo)

Различать requirement, action, observed result и accepted outcome. Каждое требование связано с проверкой и артефактом, а переход этапа зависит не от красивого child summary. Exit0 != внешний эффект, child exit != успех задачи. После сбоя сверять сохранённое намерение с реальным состоянием детей/файлов/репозитория, а не повторять действия вслепую.

В Prime уже есть factory и shell quality gates. Узкое дополнение — restart-safe state, артефакты и coverage требований, безопасное сведение независимых правок. GSD workflow documents — часть prompt/workflow contract, не гарантия enforcement сами по себе.

Эффект: меньше брошенных/повторённых задач и ложных финальных отчётов. Проверка: остановить kernel между двумя параллельными задачами и fan-in; после рестарта ни одного duplicate spawn, join ровно один раз, корректный результат и доступные свидетельства.

### 4. Контекст как управляемое представление, не единственное хранилище (Accordeon; ожидается финальная сверка)

Не путать исходную историю с тем, что видит модель. Холодные фрагменты могут заменяться адресуемыми краткими представлениями; точные детали запрашиваются по мере нужды. Сохранять недавнюю рабочую область и tool-call/result пары. Сжатие должно учитывать не только возраст, но цель задачи, полезность и стоимость повторного получения.

Prime уже хранит JSONL и full outputs, а summary сохраняет anchors/recent tail. Реальный дополнительный эффект возможен от выборочного управления provider context, а не второй копии transcript. Долговечность fold references отдельно проверяется после restart; RAM-only fold map не durable memory.

Проверка: одни и те же длинные задачи с изменением требований; точность восстановления старых команд/диффов/ошибок, успешность, input tokens/cache hit и задержка. Рекламный тезис «compact разрушает историю» к Prime не применять.

### 5. Действия привязаны к проверяемому наблюдению (oh-my-pi tools)

Сильный инструмент не только быстро исполняет команду: он сообщает область поиска, неполноту, точные ссылки и версию наблюдения; изменение валидирует, что основание действия ещё актуально. AST/структурный поиск снижает зависимость от случайного совпадения текста; ограниченный результат сохраняет путь к полному evidence.

Prime уже Rust, exact replacement, locks, limits/spill, cancel и dirty-tree guard. Поэтому паттерн не «переписать на Rust», а уменьшить ошибки конструирования поиска/правки и объём ненужного вывода. OMP hashline проверяется отдельно для сравнения.

Эффект: меньше неудачных edits, неверных совпадений и повторных чтений. Проверка: одинаковый набор repo tasks и competing edits; success/recall/output tokens/stale refusal/end-to-end time, не микробенч языка.

### 6. Память по происхождению и результату, а не по убедительности текста (RuVector/RuFlo)

Кандидат/подтверждённое/устаревшее знание; происхождение и независимость свидетельств; hybrid retrieval с фильтрацией области до/вместе с similarity. Вектора — способ искать, не источник истинности. Учиться также на неудачных действиях, не только accepted episodes.

Prime уже хранит evidence/rollback; ranking lexical+IDF. Дополнение — проверка допуска и более релевантное извлечение, если lexical baseline действительно не справляется. Policy learning только после данных; нет counterfactual о невыбранном действии, успех одного сложного задания нельзя сравнивать со скоростью другого простого.

Проверка: релевантные и опасно похожие воспоминания, противоречия, дубликаты одного источника, будущие реальные задачи. RuFlo inspected backend Map+linear cosine и simulated consensus не доказывают README speed/consensus claims.

## Другие источники

DeepSeek Harness: разделение неизменяемого event log и model view; completion events вместо polling; узкое устранение повторяющихся tool failures и oversized outputs до полного summarization. Prime много этого уже умеет; полезен паттерн диагностики повторений и bounded repair, не новый plugin framework.

Grok: исследован Grok Build как официальный harness (Grok Code Fast — модель). Роли observe/plan/execute с разными возможностями, worktree separation, rewind и sandbox. Для Prime базовые роли через subagents уже возможны; ограничение полномочий должно исполняться за пределами prompt. Worktree не sandbox.

## Приоритет

- Для персонального coding UX: Taste admission + selective advisor.
- Для долгих автономных запусков: verified durable factory continuation.
- Для длинного контекста: конкретный Accordeon delta после overlap проверки.
- Для точности работы в репо: evidence-bound tools; semantic retrieval по доказанной необходимости.
- Отложить: целые swarm frameworks, graph DB внутри ядра, LoRA/RL до outcomes baseline, глобальный advisor каждый шаг.
